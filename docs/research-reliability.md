# Отчеты и отказы поставщика

## Проверка контрпримеров

Новые задания запрашивают `counterexample-report@2`:

```json
{
  "schema": "counterexample-report@2",
  "outcome": "none_found",
  "evidence": "Проверенные случаи и основания",
  "assumptions": "Явные предпосылки",
  "limitations": "Ограничения проверки",
  "unresolved_obligations": []
}
```

Исходы: `none_found`, `counterexample_candidate`, `inconclusive`.
Для кандидата опровержения допустимо поле `refutation_source`.
Вопросы имеют поля `kind` (`mathematical` или `operational`) и `text`.
Предпосылки, ограничения и вопросы сохраняются, а неизвестные поля отклоняются.
Один JSON в именованном блоке может сопровождаться пояснениями; несколько
конкурирующих блоков не принимаются. Исходный ответ исполнителя не переписывается.

Прежние минимальные отчеты остаются допустимыми. Прежнее строковое поле
`unresolved_obligations` сохраняется как вопрос без классификации.
Система не выводит отсутствие вопросов из слов «нет» или «приемка».
Непустой список вопросов блокирует переход к готовому результату.

`GET /api/attempts/{id}/counter-report` возвращает разобранные поля, вопросы,
контрольную сумму отчета и состояние разбора. Оператор может подтвердить,
что вопросы относятся только к организации работы:

```json
{
  "attempt": "run-...",
  "report_sha256": "...",
  "note": "Основание классификации каждого перечисленного вопроса",
  "confirm": true,
  "expected_revision": 10,
  "request_id": "counter-audit-001"
}
```

Запрос направляется в `POST /api/counter-audits`. Отметка привязана к попытке,
точному результату, разобранному отчету и постановке. Изменение предпосылок
или ответа делает ее неприменимой. Явно математический вопрос таким действием
закрыть нельзя. Повторная обработка готовых ответов через команду команды
`reprocess` не создает нового обращения к модели.

Перенос отдельного результата с таким разбором пока отклоняется; нужен полный
архив области. История отметок сохраняется в SQLite и PostgreSQL.

## Допуск поставщика

Три последовательных отказа соединения либо ответа HTTP 429, 502, 503, 504
удерживают новые передачи общему адресу модели. Это свидетельства ограничения
или недоступности, а не отрицательные математические результаты.
Предел вывода, неправильный формат ответа и ошибка настройки учитываются отдельно.
Успешный ответ сбрасывает счетчик последовательных отказов, но уже установленное
удержание автоматически не снимается.

Удержание проверяется при резервировании бюджета и непосредственно перед
отправкой задания. Уже выполняющиеся обращения оно не отменяет. Очередь,
неизвестный расход и зарезервированные пределы сохраняются после перезапуска.
Автоматических повторов неизвестных передач нет. Проверочные платные запросы
для определения доступности самостоятельно не запускаются.

`POST /api/providers/commands` принимает `profile`, `kind` (`pause`, `resume`,
`note`), `note`, `confirm`, `expected_revision`, `request_id`.
У профилей с одинаковым адресом модели общий допуск. Для внешних программ
допуск разделяется по профилям: их скрытые адреса из настроек не угадываются.
Возобновление допуска само по себе не снимает общую паузу и не повторяет
завершенные попытки. Панель находится в разделе «Исполнители».

Сообщение пользователя о простое можно записать как наблюдение. Пока нет
временных границ простоя, система не назначает его причиной конкретного отказа.

## Вход проверки Lean

Поле `tool_goals` содержит доверенные определения для чтения. Кандидат должен
импортировать `Goal` и объявлять только указанную теорему; повторное объявление
цели из `tool_goals.source` нарушает привязку проверки к исходной постановке.
Поле `tool_candidate_templates` содержит отдельный шаблон для каждого
инструмента, включая точное имя отрицания. Ответ проверяющей службы также
возвращает соответствующий `candidate_template` после успеха или ошибки.
Шаблон содержит начало доказательства, а не готовое доказательство.

Два вызова инструмента могут исчерпаться раньше предела токенов. В этом случае
нужно разбирать события и `limit_reason`, сохраняя исходные ответы. Такой исход
сам по себе не свидетельствует о простое поставщика или ложности утверждения.

## Файлы рецензии

Новый вход рецензии при наличии сохраненных входов компилятора содержит
`checked_files`: отдельные `Goal.lean` с определениями и `Candidate.lean`
с доказательством. Служба читает фактические файлы проверки, сравнивает их
с закрепленной целью и исходником, затем указывает роли и суммы байтов UTF-8.
Эти суммы отличаются от сумм JSON в отчете Lean. Свидетельство происхождения
целевой декларации требует завершенного штатного аудита, а не одной компиляции.

Требование самодостаточности определений не запрещает `import Goal` в кандидате.
Соответствие естественной постановки формальной цели по-прежнему требует
отдельной проверки. Старые отчеты не переписываются; при отсутствии сохраненных
входов компилятора свидетельство о файлах не добавляется. Поврежденная или
неполная пара файлов блокирует подготовку новой рецензии.

`lean_modules` содержит точную формальную цель, постановку, предпосылки,
вид объекта, принятую версию и связь с результатом для каждого доступного
модуля достижимого основания. Это относится и к принятому покрытию вида
`obligation`. Поле `accepted_lemmas` по-прежнему содержит только леммы;
отсутствие покрытия в нем не означает, что покрытие не принято. Недействующие
и посторонние модули отбрасываются прежними проверками области и версии.

## Остановка обработки

`GET /api/health` и начальная выдача содержат `execution`: признак действующей
обработки, текущую и последнюю зафиксированные остановки. При необратимой
ошибке фоновой обработки служба сохраняет этап, время и безопасный класс
ошибки в `execution-stop.json`, затем отменяет свой контекст. Сохраняется первая
причина; последующие отмены ее не заменяют. Исходное сообщение драйвера,
строка подключения и ключи не записываются. Для PostgreSQL допустим код SQLSTATE.

`storage` отдельно сообщает состояние подключения, поколение, время и класс
последнего наблюдавшегося отказа. При повторной попытке восстановления без
соединения исходная диагностика сохраняется. Успешное подключение не означает
возобновления отмененной обработки. Перед перезапуском нужны просмотр активных
попыток, проверка неизвестных исходов и подтверждение оператора. История прежней
остановки остается после перезапуска; текущая и прошлая остановки различаются.
Сбой сохранения диагностического файла не должен отменять остановку: запись
файла выполняется по возможности, безопасный класс также направляется в журнал.

## Доставка технических заметок

Linux-программа `research-deliver-note` доставляет только записи `kind: note`
в местный `POST /api/memory`. Она не запускает модель, не принимает доказательства
и не меняет их цели. Файл заметки содержит `target`, `content`, `conditions`.

```sh
go build -o bin/research-deliver-note ./cmd/research-deliver-note
bin/research-deliver-note -outbox /private/reports \
  -enqueue-note /private/note.json -delivery-key experiment-001-final \
  -enqueue-only
bin/research-deliver-note -server-config /private/server.json \
  -outbox /private/reports -watch
```

Каталог очереди размещается вне `data_dir`, чтобы работа наблюдателя не изменяла
файлы во время резервного копирования сервера. Он должен быть закрытым каталогом
на доверенной местной файловой системе. Записи создаются атомарно с синхронизацией;
блокировка файла исключает параллельную доставку одной записи. Ключ производителя
закрепляет неизменный отчет: повторная постановка того же содержимого дает тот же
идентификатор, другое содержимое с тем же ключом отклоняется. Ключи отчетов
не должны содержать секреты. Исправленный отчет требует нового ключа.

До передачи сохраняются идентификатор команды и ожидаемая версия. При потере
ответа повторяются именно они: серверный журнал команд предотвращает повторное
добавление заметки, в том числе после перезапуска. Только явный конфликт версии
409 разрешает получить новую версию; неизвестный исход не переопределяется.
Ответы 400, 401, 403, 413 останавливают доставку этой записи до разбора оператором.
Остальные неизвестные исходы остаются в очереди. В режиме `-watch` проверка
повторяется через пять секунд. Автоматически исправлять отклоненные записи нельзя.

Соединение допускается только с буквальным адресом loopback по HTTP,
перенаправления и использование сетевого посредника запрещены. Ключ оператора
читается из доверенных местных настроек, не сохраняется в очереди и не выводится.
Это механизм повторной доставки местной команды, а не разрешение повторять
обращения к модели с неизвестным исходом.
