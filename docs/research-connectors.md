# Удаленные исполнители и Telegram

Оба модуля выключены без настройки. Регистрация соединителя не включает его для исследования. Токены хранятся в окружении или закрытом `secret_file`; значения в JSON-задания не входят.

## Удаленные исполнители

Сервер хранит задания и проверяет результаты. Удаленная программа получает задачу через HTTP API, выполняет ее собственным агентом и передает кандидат. Ее ключ не разрешает операторские действия, приемку, изменение цели или чтение общей базы.

Настройка `workers` в серверном JSON:

```json
[
  {
    "id": "worker-proof",
    "label": "Удаленный поиск доказательства",
    "token_env": "RESEARCH_WORKER_KEY",
    "profiles": ["model-proof-reader"]
  }
]
```

Ключи исполнителей должны быть разными и отличаться от ключа оператора. Оператор включает исполнителя для исследования через `POST /api/worker-bindings`: `study`, `connector`, `enabled`, `expected_revision`, `request_id`.

При запуске отдельного задания в `POST /api/attempts` укажите `remote_worker`. Команда также принимает `workers`, например `{"proof":"worker-proof"}`, вместе с картой `profiles`. Остальные роли исполняются местно.

Передаваемый состав ограничен постановкой выбранного исследования и его внутрисистемными основаниями того же исследования, связанными вопросами и результатами заданий команды, процедурами навыков, пределами и файлами `TASK.md` и `Goal.lean`. Передаются контрольные суммы этих файлов. Прочие файлы рабочей области, общая библиотека других исследований, настройки сервера и значения ключей не выдаются.

Протокол:

| Запрос | Назначение |
|---|---|
| `POST /api/workers/{id}/claim` | Получить назначенную попытку; тело содержит `request_id` |
| `POST /api/workers/{id}/attempts/{attempt}/heartbeat` | Продлить аренду; тело содержит `epoch` и `snapshot` |
| `POST /api/workers/{id}/attempts/{attempt}/result` | Передать `result` с идентификаторами, исходным снимком, эпохой и `request_id` |

Для всех запросов нужен `Authorization: Bearer <ключ исполнителя>`. Аренда продлевается на 45 секунд, но не выходит за время профиля. У одного исполнителя одновременно одна действующая аренда. Просроченный, отмененный, чужой или устаревший результат отклоняется. Истечение аренды означает неизвестный исход, без автоматического повтора.

Подготовлена команда:

```sh
go build -o bin/research-worker ./cmd/research-worker
bin/research-worker -config /absolute/path/to/worker.json
```

Файл `worker.json`:

```json
{
  "server": "http://127.0.0.1:4187",
  "worker": "worker-proof",
  "token_env": "RESEARCH_WORKER_KEY",
  "profile": "/absolute/path/to/local-profile.json"
}
```

Программа выполняет одно назначенное задание. Идентификатор местного профиля должен совпадать с назначенным; процедуры и пределы берутся из пакета. Адрес модели, ключ, команда агента и граница исполнения остаются местными настройками исполнителя. `execution_profile_sha256` фиксирует контрольную сумму местного профиля; эти сведения сообщает сам исполнитель, без аппаратного подтверждения.

Материалы записываются во временный закрытый каталог после сверки контрольных сумм. Программа передает поддерживаемые события вместе с итоговым результатом; промежуточная передача событий удаленного агента пока отсутствует.

Сервер слушает локальный адрес. Для первого удаленного подключения используйте SSH-перенаправление с портом `4187` на обеих сторонах, чтобы сохранилась проверка `Host`. Публичное размещение требует отдельного проекта доступа, TLS и ограничений запросов. Живое подключение выполняют после выбора получателя и утверждения передаваемых материалов.

Отключение соединителя прекращает выдачу новых заданий и прием результатов по этой связи. Уже работающая внешняя программа остановится после следующего отказа продления аренды; мгновенная остановка удаленного процесса не гарантируется.

На выбранной машине исполнителя перенаправление создают командой `ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:4187:127.0.0.1:4187 USER@COORDINATOR`. Значения `USER` и `COORDINATOR` заменяют утвержденными. Затем программа использует `http://127.0.0.1:4187`; занятый местный порт требует согласовать новый порт и допустимый `Host`, а не отключать проверку. Ключ передают через закрытое окружение, без параметра командной строки.

Общий [бюджет исследования](study-budget.md) распространяется и на удаленные попытки. Аренда ограничена сроком исследования. Результат после срока отклоняется даже до следующего прохода планировщика.

## Telegram

Модуль использует `getUpdates` для сообщений и `sendMessage` для ответов. При отсутствии конфигурации или включенной связи он не обращается к Telegram. `GET /api/studies/{id}/report` и кнопка «Просмотреть отчет» показывают текст состояния без отправки, создания сообщения или обращения к Telegram. Просмотр доступен оператору даже без настроенного бота.

Серверный массив `telegram` содержит:

```json
[
  {
    "id": "research-chat",
    "label": "Чат исследования",
    "token_env": "RESEARCH_TELEGRAM_TOKEN",
    "chat_id": -1000000000000,
    "allowed_user_ids": [123456789]
  }
]
```

Идентификаторы примера заменяют настоящими. Один чат связывают с одним включенным исследованием. Веб-интерфейс содержит выключатель связи, форму сообщения и команду отправки состояния исследования.

`POST /api/telegram/bindings` принимает связь исследования и канала. `POST /api/telegram/messages` принимает текст либо `status_report=true` и обязательное `confirm=true`. Обе команды требуют версии и идентификатора запроса.

Входящий текст принимается только из заданного чата и от разрешенного пользователя. Он создает вопрос и задание ответа, без автоматического оплачиваемого запуска. Ответ агента сохраняется в системе; отправку текста в чат отдельно подтверждает оператор. Повторный номер сообщения не создает второй вопрос. Команда `/status` помещает отчет в очередь отправки.

Намерение отправки записывается до обращения к Telegram. При ошибке или перезапуске во время отправки исход считается неизвестным; автоматического повторного сообщения нет. Оператор сверяет чат перед новой отправкой. Отключенная связь не получает и не отправляет сообщения.

Модуль пока передает текст, без вложений и потоковых отчетов. Для одного бота должен работать один получатель `getUpdates`; совместная работа с другим получателем или доставкой через HTTP-уведомления не предусмотрена.

## Испытания

Сценарии BDD проверяют выключенное состояние, область доступа исполнителя, эпоху аренды, повтор команды, отсутствие операторских полномочий, разрешенных участников Telegram, повтор входящих сообщений и неизвестный исход отправки. Испытания используют местные подставные службы. Действующие ключи и живые внешние подключения для этих проверок не требуются.

Шаблоны находятся в `examples/connectors`: `worker.json` задает местную программу исполнителя, `server-fields.json` содержит поля для регистрации двух модулей. Регистрация сама по себе не включает связь. До подключения нужно выбрать удаленную машину, создать отдельный ключ исполнителя, утвердить каталог материалов; для Telegram нужны токен бота, настоящий `chat_id` и список `allowed_user_ids`. Значения шаблона чата предназначены только для замены и не указывают действующего получателя.
