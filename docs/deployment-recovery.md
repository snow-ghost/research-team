# Автозапуск и восстановление

## Ошибки конфигурации

Сервер возвращает код 78 при ошибке загрузки доверенной конфигурации. Шаблон службы содержит `RestartPreventExitStatus=78`; исправлять неверную конфигурацию повторными запусками служба не пытается. Ошибки соединения с базой после загрузки конфигурации сохраняют обычный код отказа и допускают повторный запуск согласно `Restart=on-failure`.

После исправления настроек или подключения носителя оператор выполняет `systemctl --user restart research-team.service`. Исторические среды Lean и отчеты не переписываются. При изменении точки монтирования создается новая рабочая конфигурация с прямыми путями к тем же версиям зависимостей.

## Пользовательская служба

PostgreSQL запускается текущим Docker Compose. Go-сервер работает на локальном адресе под пользовательской службой systemd. Размещение в открытой сети, TLS и несколько операторов в этот порядок не входят.

```sh
go build -o bin/research-server ./cmd/research-server
go build -o bin/research-backup ./cmd/research-backup
go build -o bin/research-quiesce ./cmd/research-quiesce
go build -o bin/research-service ./cmd/research-service
bin/research-service -root "$PWD" \
  -config /absolute/path/to/private-server.json \
  -env "$PWD/.env.postgres" -out /absolute/path/to/new-private-units
```

Файл окружения должен иметь права `0600`. Генератор создает три файла с подставленными путями, но не устанавливает их автоматически. Перед установкой:

```sh
systemd-analyze --user verify /path/to/units/research-team.service \
  /path/to/units/research-team-backup.service \
  /path/to/units/research-team-backup.timer
install -d -m 700 "$HOME/.config/systemd/user"
install -m 600 /path/to/units/research-team* "$HOME/.config/systemd/user/"
systemctl --user daemon-reload
systemctl --user enable --now research-team.service
systemctl --user enable --now research-team-backup.timer
```

Для запуска без входа пользователя применяется `loginctl enable-linger USER`, если это разрешено политикой машины. Сервер после аварии не повторяет незавершенные платные операции: для них сохраняется прерванный или неизвестный исход.

## Rootless-подключение Lean

Основной сервер может не иметь доступа к Docker socket. В этом случае на узле с закрепленными Lean и Docker отдельно запускается непривилегированная служба:

```sh
go build -o bin/research-lean-service ./cmd/research-lean-service
RESEARCH_LEAN_SERVICE_TOKEN='отдельный-секрет-не-короче-32-символов' \
  bin/research-lean-service -config /absolute/path/to/lean-check.json
```

Служба слушает только `127.0.0.1:4189` по умолчанию и предоставляет `POST /v1/check`, `POST /v1/match`, `POST /v1/prepare`, `POST /v1/build`, `POST /v1/inspect` и `GET /healthz`. Цепочки лемм, повторное использование и представления используют `/v1/check`; локальный каталог для сохранения отчета создается и при `InspectModule`. Подготовка целей, проверка с сохранением артефактов и сборка модулей используют `artifact-root` (по умолчанию рабочий каталог службы): абсолютный каталог артефактов клиента должен существовать внутри этого корня и не быть symlink. Если `dir` в `/v1/check` не задан, проверка использует временный каталог без сохранения `Candidate.olean`. Параметр `artifact-alias` (по умолчанию `/src`) отображает контейнерный префикс в `artifact-root` и применяется также к каталогу модуля в `/v1/match`. В `/v1/check` клиент передает полный список библиотек закрепленной среды: базовый префикс должен совпадать с конфигурацией службы, а дополнительные модули разрешаются только внутри `artifact-root`. Служба сохраняет остальные параметры своей конфигурации и возвращает сумму фактической среды; клиент сравнивает ее с суммой закрепленной среды. Клиент повторно проверяет полученные файлы локально. В конфигурации основного сервера задаются тот же `lean_config`, `lean_service_url` и `lean_service_token_env`. Для сервера в контейнере допускается `host.docker.internal`; другие сетевые адреса и HTTPS в этом режиме не поддерживаются. Токен передается только через окружение, не записывается в конфигурацию. Клиент отключает прокси и перенаправления, проверяет суммы цели, исходника, артефактов и процедур. Историческая среда не заставляет сервер обходить службу прямым запуском Docker.

Это разделение прав, а не rootless Docker daemon: учетной записи Lean-службы по-прежнему нужен разрешенный доступ к ее Docker. Основной веб-сервер такого доступа не получает. Проверка и сопоставление выполняются с прежними ограничениями `DockerChecker`; HTTP не заменяет аудит ядра и не принимает математический результат.

На macOS основной сервер и Lean могут работать как два пользовательских LaunchAgent. Локальные plist хранятся вне Git в `.research-server/launchd` и устанавливаются в `~/Library/LaunchAgents` с правами `0600`; секреты в репозиторий не копируются. Метки этой установки: `com.snowghost.research-team-server` и `com.snowghost.research-team-lean`. Проверка состояния: `launchctl print gui/$(id -u)/LABEL`; принудительный перезапуск: `launchctl kickstart -k gui/$(id -u)/LABEL`. `RunAtLoad` и `KeepAlive` включены, повторный запуск ограничен десятисекундной паузой. Журналы находятся в `.research-server/logs`. Перед испытанием восстановления нужно убедиться в отсутствии активных попыток; аварийный перезапуск не разрешает повтор неизвестного обращения к модели.

Статический токен Lean периодически заменяют одновременно в обоих plist, не выводя новое значение в журнал. После установки файлов с правами `0600` обе службы выгружают через `launchctl bootout` и снова загружают через `launchctl bootstrap`: `kickstart` не перечитывает измененный plist. Старый токен после этого не принимается. Другие evaluation-экземпляры также нужно остановить или обновить отдельно. Исторические отчеты проверки не содержат токен и не изменяются при ротации.

## Проверяемая копия

По умолчанию таймер срабатывает ежедневно в 04:00 местного времени. Служба сначала приостанавливает допуск новых запусков, ожидает завершения попыток, проверок и сборок, затем останавливает сервер. Копия создается в закрытом постоянном каталоге `.research-backups`, вне каталога состояния. Проверяются все таблицы и файлы, а также пробное восстановление. Сервер запускается после завершения команды, включая ошибочный исход копирования.

Ключ входа и файл блокировки не копируются. Другие закрытые настройки внутри состояния могут содержать ключи; весь каталог копии должен оставаться закрытым. `.research-backups` исключен из Git. Копия на том же диске не защищает от потери машины: перенос копий на отдельный носитель остается задачей оператора.

Если Docker socket запрещен даже отдельной backup-программе, остановите сервер и создайте отдельный клон базы, затем проверьте его `scripts/check-postgres-backup.mjs`. Research-артефакты `attempts` и `verifications` можно скопировать отдельно и сравнить `diff -r`, исключив ключи и operational configuration. Такой снимок не является полной резервной копией для автоматического восстановления службы: он проверяет данные исследований, но не восстанавливает секреты и настройки запуска.

Для локальной установки на macOS полный сценарий автоматизирован командой `RESEARCH_TEAM_CONFIG=/absolute/private/server.json RESEARCH_BACKUP_ROOT=/absolute/private/root scripts/backup-launchd.sh`. Он через `research-quiesce` приостанавливает новые запуски и ожидает активные операции до двадцати минут, останавливает основной LaunchAgent и ждет освобождения блокировки. `research-backup` сохраняет базу и все research-файлы состояния, включая библиотеки и подготовленные модули, сравнивает таблицы и суммы файлов и проверяет пробное восстановление. После перезапуска `research-quiesce -release` снимает maintenance и возобновляет прежнюю разрешенную очередь; при ошибке копирования выполняется тот же перезапуск. Ежедневный запуск в 04:00 выполняет отдельный LaunchAgent `com.snowghost.research-team-backup`, журналы находятся в `.research-server/logs`.

Maintenance-утилиты работают в отдельном Linux-контейнере без Docker socket. Резервное копирование и восстановление используют официальный PostgreSQL client-контейнер с `-local-postgres`: команды `pg_dump`, `pg_restore` и `createdb` обращаются к базе по TCP через `host.docker.internal`, а DSN из закрытого env-файла или переменной `RESEARCH_DATABASE_URL` среды LaunchAgent преобразуется только внутри процесса; сценарий передаёт переменную в контейнер без вывода её значения. Ключ входа и блокировка не копируются, но другие закрытые настройки и секреты исполнителей внутри состояния сохраняются: весь каталог копии должен оставаться закрытым.

После отдельного копирования `research-backup` сервер остается приостановленным. Продолжение разрешается оператором в интерфейсе или командой `research-quiesce -release`. Ожидание работающих процессов ограничено двадцатью минутами. Очередь незапущенных попыток и нативных проверок закрепляется отдельной командой обслуживания: задачи сохраняются после перезапуска без выполнения. Попытки должны иметь `not_started`, без зафиксированного входа или результата. Неподтвержденная очередь после аварии обрабатывается прежним механизмом прерванного исхода. Автоматического удаления, отмены или повторения неизвестного обращения нет.

`POST /api/maintenance` с подтверждением закрепляет очередь при глобальной паузе. Поле `kind: "release"` снимает режим обслуживания, оставляя новые обращения к моделям на паузе. Обычное снятие глобальной паузы также завершает обслуживание, но уже допускает разрешенную очередь к исполнению.

Координатор проверяет номер версии базы каждые 100 мс. Полное чтение и проход по состоянию выполняются после изменения версии либо наступления ближайшего срока исследования или удаленной попытки. `GET /api/metrics/scheduler` возвращает число таких проходов, полных чтений и проверок версии; маршрут требует обычного входа.

## Переносимый комплект

```sh
bin/research-backup -portable-from /path/to/verified-backup \
  -out /path/to/new-private-portable-kit
```

Команда переносит снимок PostgreSQL и каталоги попыток, проверок, библиотеки, извлечения типов и состояния соединителя Coddy. Эксплуатационные каталоги, включая настройки запуска и ключ входа, не копируются. База и рабочие артефакты остаются закрытыми: команда не проверяет наличие секретов внутри исторических материалов. Перед передачей на другой узел требуется проверка содержимого.

Для нового узла нужны отдельно установленные программы, библиотеки Lean и новая конфигурация. Переносимый комплект не содержит образ системы или ключи модели. Исходная копия и ее манифест не изменяются; комплект имеет собственный перечень сохраненных файлов.

## Новый экземпляр

Для восстановления подготовьте отдельную конфигурацию: новую базу с именем `research_restore_...`, несуществующий каталог состояния, другой локальный порт. Ссылку на DSN задайте отдельной переменной окружения. Отключите внешние исполнители, Telegram и удаленные модули; не передавайте ключ рабочего интерфейса.

```sh
bin/research-backup -config /path/to/private-restore-server.json \
  -restore /path/to/verified-backup
```

Команда проверяет завершенный манифест, суммы базы и файлов, создает новую базу, восстанавливает ее и сравнивает содержимое. Исходные владельцы и команды `GRANT/REVOKE` не переносятся; доступ определяется выбранной ролью нового экземпляра. Существующая база и каталог не перезаписываются. При ошибке новый экземпляр сохраняется для разбора. Ошибка соединения при проверке отличается от несовпадения сумм. До запуска приложения записывается отдельная команда паузы; исторические доказательства и отчеты не редактируются.

Для TCP client-контейнера добавьте `-local-postgres`; параметр `-restore-database research_restore_...` заменяет имя базы в DSN внутри процесса и позволяет использовать прежний закрытый env-файл без копирования секретов.

Запустите новый сервер, проверьте исследования, профили, библиотеку и выполните отдельную новую проверку Lean. Версии Lean, библиотеки и исполняемые файлы должны быть установлены и заданы в конфигурации нового экземпляра. Абсолютные пути исторических отчетов автоматически не заменяются. Смена среды требует новой проверки и, при необходимости, новой сборки модулей, а не изменения старых контрольных сумм.

На текущей установке снимок `20261103T095244Z` восстановлен в изолированную БД и новый каталог: совпали 33 таблицы и 288 файлов, прочитано 21 исследование. Новая проверка `verify-da0f4fab5783ff8d715c7cf4093be7e2` на отдельном сервере и отдельной Lean-службе завершилась `verified` без аксиом. После приемки recovery-процессы и тестовая БД удалены. Автоматический снимок `20261103T102502Z` также завершил полный цикл с повторной разблокировкой основного сервера.

Местная приемка отдельного процесса и базы не заменяет испытание на другой машине. Живое удаленное подключение требует выбранной машины и отдельного разрешенного ключа.

Для местного испытательного PostgreSQL подготовлен [отдельный Compose](../deploy/recovery/compose.yaml). Он использует отдельный том, отдельный пароль и порт `127.0.0.1:55435`. Сеть bridge допускает исходящие соединения; она не дает сетевой изоляции от внешних адресов. Ключи моделей и рабочая конфигурация в этот экземпляр не передаются. После приемки контейнер останавливается, том сохраняется. Новая проверка Lean выполняется через изолированную проверяющую службу. Адрес SSH для приемки на другой машине задается отдельно.
