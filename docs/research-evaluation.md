# Подготовка нового сравнения

## Наблюдение выполнения

Необязательный массив `evaluations` в закрытой конфигурации сервера подключает наблюдение существующего опыта:

```json
{
  "evaluations": [
    {
      "id": "educational-comparison",
      "label": "Сравнение на учебных задачах",
      "file": "/private/comparison/report.json",
      "configuration_sha256": "REPLACE_WITH_64_LOWERCASE_HEX_DIGITS"
    }
  ]
}
```

Значение суммы заменяют точной суммой конфигурации из отчета запущенного опыта. Поддерживается до десяти записей. Отчет должен находиться вне веб-каталога; его размер ограничен 8 МиБ. API оператора `GET /api/evaluations` возвращает только состояние, числа завершенных запусков, обращения и резервы, сводку и обозначения текущих назначений. Постановки, ответы, настройки, ключи и местный путь не выдаются. Интерфейс обновляет сведения каждые пять секунд.

При отсутствии файла показывается состояние «Не начато». Отчеты имитации, другой конфигурации или несовместимой политики отклоняются. Наблюдение не запускает и не возобновляет опыт. Итоги до окончания всех назначений остаются промежуточными; доступные сведения не подтверждают общего преимущества какого-либо режима. Приемка математических результатов выполняется отдельно.

## Набор задач

Набор `examples/evaluation-cases.json` содержит двенадцать известных учебных постановок: по две задачи о полиномах, делимости, конечных множествах, логике, функциях и конечных суммах. Имена имеют вид `task-NNN` и не содержат ожидаемого исхода. Файл не содержит ответов или доказательств. Новизна математических утверждений не заявляется. Обезличенные имена не исключают знакомства модели с задачами при предварительном обучении.

```sh
go run ./cmd/research-eval-plan -cases examples/evaluation-cases.json
```

Команда проверяет структуру набора, идентификаторы, число классов и постановки, затем выводит суммы набора и политики. Она не вызывает модель, не компилирует Lean, не изменяет базу и не разрешает расходы. `mathematical_verification` остается ложным.

План предусматривает два повторения и четыре режима: один исследователь, фиксированная команда, специалисты по необходимости и местный контроль Lean. Всего 96 записей. При шести обращениях на каждый режим с моделью общий верхний предел составляет 432 обращения. Это расчет плана, не разрешение запуска. Версия 4 программы сравнения поддерживает этот набор и закрепляет суммы набора, правил назначения и программы аудита. Прежние версии 2 и 3 сохраняют шесть задач. Живой запуск требует отдельного подтверждения материалов, модели и общего бюджета.

## Испытание порядка без модели

```sh
go run ./cmd/research-eval-plan -cases examples/evaluation-cases.json \
  -rehearse-out /private/new-rehearsal
go run ./cmd/research-eval-plan -cases examples/evaluation-cases.json \
  -rehearse-out /private/new-rehearsal -resume
```

Испытание использует тот же порядок назначения, записи и возобновления, заменяя исполнителя и Lean местными имитаторами. Ключи и серверные настройки не читаются, обращений к модели и запусков Lean нет. Отчет содержит `simulation: true`, его импорт как живого сравнения запрещен. Числа успешных проверок внутри такого отчета описывают ответы имитатора, без математического подтверждения.

Закрытая конфигурация живого опыта проверяется без загрузки учетных данных:

```sh
go run ./cmd/research-compare -config /private/comparison.json -validate-only
```

Повтор с `-resume` не исполняет завершенные назначения. Изменение набора или попытка продолжить имитацию как живой опыт блокируется. Для живого опыта используется `research-compare` с закрытой конфигурацией версии 4 и отдельным `-confirm`; предел составляет 432 обращения. При возобновлении прерванные обращения удерживаются без автоматического повторения.

Предварительная местная проверка `TestEvaluationBDD_RealLeanCompilesEveryGoalWithoutAcceptingSyntheticProof` компилирует каждую постановку и удостоверяется, что искусственный незавершенный кандидат отклонен аудитом. Это проверка входных целей, не получение математических результатов.

## Контрольный пример wrapped 4-cycles

Локальная попытка `run-54afe35e09c6552de4c959955937af4b` проверила порядок «сначала контрпример» на всех 5040 перестановках семи позиций. Серверные артефакты содержат эксцентриситет 6, кратчайшее слово полного flip длины 5 и независимое `shortest: true`. Поскольку Cayley-граф вершинно-транзитивен, эксцентриситет старта является диаметром; полный flip не является диаметральным состоянием.

То же слово `[left 0, left 1, left 6, left 0, left 5]` проверено отдельно в Lean 4.34.0 теоремой `fullFlip7Ops_correct`, без аксиом. Линейные операции `left4/right4` не используются для этого сертификата: заворачивание блока реализовано отдельными `leftWrapped4/rightWrapped4`. Общая формула диаметра и случай повторов этим результатом не доказываются. Прежние таблицы BFS считаются недоверенными материалами, а не свидетельствами.

Для бинарного случая `d = n−1` доказана отдельная точная формула: `1, 2, 2` при `n = 5, 6, 7`; при `n ≥ 8` и `n = 6q+r` диаметр равен `q+1` плюс ещё единица при `r=4`. Доказательство использует положение уникального символа и `rep(x)=⌊x/3⌋+(x mod 3)`. Верхняя оценка и достигающий свидетель формализованы в `Repeated.lean`; базовые случаи проверены ядром. Ранее предложенная линейная формула `floor((n+8)/6)` не подтвердилась и не используется: например, при `n=11` диаметр равен 2, а не 3. Общий случай повторов остаётся открытым.

Гипотеза `D(n,2)=n−2` также отвергнута. Независимый перебор 1 814 400 состояний при `n=10,d=2` дал диаметр 9, а полный flip — 8. Это контрпример и к линейной формуле, и к представлению полного flip обязательно диаметральным состоянием. Слова для обоих состояний проверены независимо в Go и Lean: flip получается восемью операциями `twoCopies10FlipOps`, а состояние `[8,7,8,6,5,4,3,2,1,0]` — девятью операциями `twoCopies10FarOps`. Кратчайность flip подтверждает исчерпывающий перебор; ограниченный серверный BFS не выдает здесь сертификат минимальности из-за предела в 20000 состояний. Lean проверяет сами слова, а исчерпание и минимальность диаметрального свидетеля обеспечивает перебор. Общая формула для двух копий пока не доказана.

Для `n=11` добавлена воспроизводимая офлайн-команда `research-graph-search`; две независимые реализации на C++ и Go исчерпали компоненты и дали совпадающие значения. При `d=2` проверено 19 958 400 состояний, диаметр 10 и flip 10. При `d=3` — 6 652 800 состояний, диаметр 10 и flip 9; при `d=4` — 1 663 200 состояний, диаметр и flip по 9. Для `d=2` слова flip и отдельного диаметрального состояния `[4,3,2,1,0,9,9,8,7,6,5]` проверены в Go и Lean (`twoCopies11FlipOps`, `twoCopies11FarOps`). Исчерпание доказывает значения только для этих конечных компонент; общей формулы нет.

Переход от эксцентриситета старта к диаметру компоненты с повторами обоснован отдельно. Перестановки значений транзитивно действуют на arrangements фиксированного мультимножества и коммутируют с позиционными ходами, поэтому граф вершинно-транзитивен. Коммутация формализована теоремами `leftWrapped4_map`, `rightWrapped4_map` и `applyWrappedOps_map` без новых аксиом. Транзитивность действия следует из сопоставления позиций одинаковых символов.

При `n=12` воспроизводимый C++-перебор показал диаметр 12 и flip 10 сразу для `d=2,3,4`: состояний 239 500 800, 79 833 600 и 19 958 400 соответственно. Для `d=2` слова flip и состояния `[4,3,2,1,0,10,10,9,8,7,6,5]` формализованы в `twoCopies12FlipOps` и `twoCopies12FarOps`. Шаблон совпадает с диаметральным состоянием при `n=11`, но пока доказывает только конкретные конечные случаи, а не общую формулу. При `n=13,d=4` перебор 259 459 200 состояний дал диаметр 13 и flip 12, что дополнительно различает поведение диаметра и flip.

Целевой расчет `scripts/near_binary_bfs.py` исследовал `d=n-r` для `r=1…5` и всех допустимых `n=8…16`: это продолжение бинарного случая с малым числом уникальных символов. Независимый 128-битный генератор `scripts/near_binary_bfs128.cpp` совпал с этими результатами и расширил случай `r=2` до `n=32`: для всех 25 значений `n=8…32` диаметр равен `⌈n/3⌉`, flip равен 3. Диаметральные свидетели образуют устойчивые семейства слов, удлиняющиеся на два хода при увеличении `n` на три. Последующий расчет до `n=32` для `r=3,4,5` дал новые закономерности: `D_3(n)=⌊n/2⌋` плюс единица при `n mod 6=1,5`; `D_4(n)=⌈2n/3⌉−1` плюс единица при `n mod 6=0`; при `n≥10` `D_5(n)=n−⌊n/5⌋−1` плюс единица только при `n=20,25,26,30,31,32,35,36,37,38,40`; отдельное `D_5(9)=6`. Формулы для `r=3,4` подтвердились дополнительно до `n=40`, для `r=5` кусочная закономерность учтена до `n=40`. Для `r=3,4,5` flip стабилизируется соответственно на 5 с `n=10`, на 8 с `n=16` и на 12 с `n=19`; начальные значения до этих границ отличаются. Эти формулы подтверждены только исчерпывающим перебором до 32 и не считаются доказанными общими утверждениями; прежняя асимптотическая гипотеза `(r−1)n/r` для `r=3,4` отвергнута. Число состояний во всех 65 отчетах совпало с `n!/(n-r)!`. Для `r=1` подтверждена ранее доказанная формула. Для двух уникальных символов (`r=2`) во всех девяти случаях диаметр равен `⌈n/3⌉`, а flip — 3. Это вычислительно подтвержденная закономерность, но общая формула диаметра остается гипотезой до доказательства обеих оценок. При `n≥10` flip во всех случаях достигается общим словом `[left(n−3), left(n−4), right(n−2)]`. Теорема `twoUniqueFlipOps_correct` в `Wrapped4.NearBinary` доказывает это для произвольных `n≥10` и произвольных двух уникальных значений на повторяющемся фоне; длина слова формализована отдельно. Нативная сборка модуля и сопоставление с новой целью `TargetStatement` завершились `verified` без модельных обращений: matcher связал все пять параметров, открытых предпосылок нет, повторная проверка использует только разрешенные `propext` и `Quot.sound`. Впоследствии определения операций вынесены в легкий `Wrapped4.Core`: при 2 ГиБ сборка по-прежнему отклоняется по памяти, а при 4 ГиБ сборка и matcher возвращают `verified`. В основном каталоге опубликован `library-844065f574050007f21f44f80e8fa997`; проверка `verify-583e2f43510632f1a44f5dc4adf1ed2b` и применение к новой цели прошли, повторный match на основном сервере с лимитом 4 ГиБ также `verified`. Исторические среды не переписывались. Воспроизводимая проверка включена в `scripts/check-research-artifacts.sh`.

## Нативный библиотечный baseline

На отдельной чистой evaluation-базе собраны и проверены две леммы. Последующий целевой перебор одной замены с одной вставкой и двух замен с одной вставкой не дал ни одного слова длины `n−1`; это ограниченные классы, не отсутствие решения вообще. Встречный поиск `scripts/near_binary_bidirectional.cpp` завершил глубину 7 от старта и 8 от flip без встречи, поэтому путь до 15 отсутствует. Продолжение до 9 нашло встречу с суммарной глубиной 16. Таким образом, точное расстояние flip для `r=8,n=16` равно 16, а не `n−1=15`. Восстановленное слово `L15 L14 R0 L14 R11 L14 L13 L11 R5 R6 L8 L4 R6 L8 L7 R5` независимо проверяет `scripts/near_binary_bidirectional_witness.py`: первая половина длины 7 дает состояние встречи, вторая длины 9 завершает flip. Теоремы `eightUniqueFlip16Ops_correct` и `eightUniqueFlip16Ops_length` подтверждают слово и длину 16 в Lean без аксиом; отсутствие пути до 15 обеспечивает исчерпывающий встречный перебор, а не Lean-теорема.

Новый `scripts/r8_induction_search.py` проверил прямое использование, удаление, замену, одну и две вставки, а также одну вставку после сдвига индексов суффикса. Переходы `15→16`, `16→17`, `15→17` и `16→18` в этих классах кандидатов не дали. Контрольный класс `15→16` согласуется с отсутствием слова длины 15 по BFS. Эти отрицательные результаты ограничены перечисленными преобразованиями и не доказывают отсутствие общего макроса; найденный в будущем кандидат остановит проверку до независимой сертификации.

## Пилот с preflight в research-agent

`research-agent` поддерживает `-preflight-declaration`, `-preflight-candidate`, `-preflight-theorem` и `-preflight-outcome`. Проверка выполняется после модели, до выдачи результата: отклонение получает `status=failed` и `preflight_rejected`, а usage и диагностика сохраняются. По умолчанию автоматических повторов нет. Необязательный `-preflight-repair` разрешает ровно один дополнительный вызов исполнителя с исходным ответом, ошибкой и контрактом; второй отказ окончателен, транспортные ошибки не исправляются. Поле `preflight` сохраняет оба кандидата и число вызовов, события объединяются, а суммарный usage помечается неполным, если расход хотя бы одной попытки неизвестен. Это ограничение на вызовы исполнителя; фактические модельные обращения отдельно считаются по событиям протокола.

На библиотечной цели и отрицании выполнено ровно 8 обращений по четыре профиля на тип. Все ответы отклонены встроенным preflight: неподходящий исход, `Mathlib`, лишние поля JSON или нарушение тактического контракта. Суммарно 2042 входных и 1021 выходной токен. Это отрицательный протокольный результат, а не оценка научной ценности профилей. Полная абляция не запускалась.

Режим `-portfolio` вместо фиксированного кандидата независимо пробует шесть нативных тактик на новых состояниях доказательства.

Новая цель `Research220` проверяет длину `sixUniqueFarOps` при переходе `n → n+1`. Шесть нативных тактик ее не закрыли с нулем вызовов, после чего четыре профиля получили по одной попытке и одному repair, всего 8 обращений, 3523 входных и 1316 выходных токенов. ## Серверный native-first

При `lean_config` серверные `proof` и `formalize` сначала проверяют библиотечные применения и шесть нативных тактик, затем вызывают модель только после неуспеха. `MatchReport.Source` передается в `library_search` и используется без повторной генерации, поэтому подстановки Lean не теряются. Для `decide` раскрываются как внешняя цель, так и ее исходные определения; общий `intros` для этой ветки не используется.

Настоящий probe с pinned checker показал: `Research202` решена одной библиотечной попыткой с `library_applications=1` и `fallback_calls=0`; `Research209` решена `decide` с `fallback_calls=0` и пустым списком аксиом; `Research220` после шести неуспешных тактик получила `model_fallback=true`. Native hit rate набора 2/3. Проверки сохраняют точную цель исходника и отчет, неуспех нативной процедуры не считается доказательством отсутствия доказательства.

## Закрепленные условия

Все режимы получают одну цель, модель, библиотеки и одинаковые общие ограничения: шесть обращений, 32768 выходных токенов на ответ и 900 секунд на режим, включая исправления и рецензию. Материалы одного режима не передаются другому. Отдельный профиль рецензента общий для режимов с моделью; независимость назначения не означает независимость модели. Навыки, разрешенные инструменты и политика исправления формата закрепляются до опыта.

Основной показатель: доля точных постановок или отрицаний, прошедших Lean и независимую рецензию без открытых существенных замечаний. Отдельно учитываются успешный Lean без рецензии, подтвержденный контрпример, нерешенная задача, ошибка формата, ошибка поставщика, превышение предела, запросы, полные и неполные измерения токенов, время и действия оператора.

Основное сопоставление использует полные парные группы с одинаковой целью и номером повторения. Отмененная извне группа сохраняется в полном отчете, но исключается из парной части целиком. Обычные завершенные технические ошибки не исключаются по признаку неуспеха. Неизвестные расходы не заменяются нулем, неизвестные обращения не повторяются.

Два повторения одной постановки не считаются двумя независимыми задачами. Результаты приводятся также по классам и постановкам; интервалы неопределенности должны учитывать группировку по задаче. Приемка результатов оператором не входит в автоматический итог сравнения. Изменение набора, ограничений или правил требует новой суммы политики и нового опыта.
