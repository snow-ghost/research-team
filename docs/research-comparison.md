# Сравнение одного исследователя и команды

## Продолжение и сводка

`research-compare -resume` продолжает только неначатые сочетания задачи, состава и повторения. Завершенные ошибки и отмененные запросы сохраняются. Для сменившихся точек монтирования предусмотрен явный параметр `-resolve-lean-paths`: он разрешает текущие ссылки к тем же каталогам Lean, сохраняя первоначальную конфигурацию опыта и ее сумму. Суммы исходной и фактической среды добавляются в `environment_resolutions`. Замена версии Lean, образа или состава библиотек этим параметром не выполняется.

```sh
go run ./cmd/research-summary -report /private/comparison/report.json \
  -out /private/new-summary.json
```

Сводка разделяет все записанные запуски и парные группы с одинаковой целью и номером повторения. Группы с отсутствующим составом, незавершенным временем или отмененным обращением исключаются из парной части. В ней сохраняются технические ошибки обычных завершенных попыток: успешный Lean и ошибка рецензии учитываются отдельно. Неизвестные токены отмечаются счетчиком неполных измерений; сумма известных токенов не выдается за полный расход.

Частичный отчет допускает местный анализ, но не импортируется как завершенное сравнение. Сводка не выполняет приемку гипотез и не устанавливает общего преимущества состава исполнителей.

## Вариант 3

`version: 3` сохраняет шесть известных задач, два повторения, предел шести обращений и 900 секунд на каждый режим с моделью. Общий максимум: 216 обращений. Предел одного ответа: 32768 токенов. Ограничение времени относится ко всему режиму, включая исправления и рецензию, а не добавляется заново для каждого специалиста.

Режимы: `single`, `team`, `demand`, `lean`. В `demand` первый исследователь возвращает формальный кандидат. Если он проходит Lean, отдельный формализатор пропускается. При отсутствии исходника или ошибке проверки формализатор получает кандидат и диагностику. Проверка границ и независимая рецензия остаются обязательными. Фиксированная команда сохраняет отдельный этап формализации; один исследователь самостоятельно выполняет исследовательские действия, после которых работает общий отдельный рецензент.

Для всех составов применяется `proof-review@2`. Независимость означает отдельное назначение и профиль, а не другую модель. Контрольная группа выполняет `lean-tactics@1`: каждая тактика начинает с нового состояния доказательства. Отчет закрепляет `policy_sha256`; изменения политики требуют нового опыта. Варианты 1 и 2 и их исходные результаты сохраняются.

Поле `mathematical_status` отражает формальную проверку отдельно от ошибки исполнения и исхода рецензии. `stages` хранит время, расход, причины завершения модели и ограничения по ролям. При наличии сохраненной диагностики фиксируется числовой код HTTP ошибки поставщика; старые случаи без такой диагностики не получают предполагаемый код. Отсутствующий расход не считается нулевым. Импорт полного отчета требует 48 завершенных записей, без приемки гипотез.

Задачи известны, набор небольшой и не является слепым испытанием. Имя одной из прежних задач содержит признак ложного утверждения; все составы получают одинаковую постановку, но этот набор не оценивает самостоятельное открытие неизвестной истины. Вывод об общем преимуществе состава из такого опыта не следует.

## Расширенный опыт

Поле конфигурации `version: 2` включает шесть задач разных классов, два повторения и четыре режима: один исследователь, фиксированная команда, адаптивная команда и контрольная группа Lean без модели. Набор постановок находится в [examples/controlled-cases.json](../examples/controlled-cases.json). Для этого варианта поддерживаются собственные исполнители через API модели.

Каждый режим с моделью получает общий предел 900 секунд и шести обращений, включая исправления и независимую рецензию. Максимум опыта составляет 216 обращений. Неиспользованный резерв шага освобождается по измеренным событиям; неизвестное обращение остается учтенным. Для контрольной группы выполняется закрепленная последовательность тактик без модели и без рецензии агента. Ее успешная проверка обозначается `verified_baseline_not_accepted`.

До первого обращения к модели проверяется компиляция всех постановок. Отчет закрепляет конфигурацию и программу аудита. Порядок трех режимов с моделью меняется по задаче и повторению. Исходники ответа не исправляются вручную: неуспешная итоговая проверка может породить новое обращение с диагностикой в оставшемся бюджете.

Каталог результатов разрешается в абсолютный путь. Отчет записывается через временный файл и замену. Продолжение проверяет завершенные предварительные проверки целей, неизменность конфигурации и аудита; начатое сочетание задачи, режима и повторения не выполняется заново. Прерванный запрос не превращается в новый разрешенный запрос.

Для импорта завершенного варианта 2 требуются 48 записей. Веб-таблица показывает режим, номер повторения, измеренные запросы, верхнюю оценку, токены и время. Сбор данных не меняет приемку утверждений. Пока опыт не завершен, программа сохраняет текущий отчет в закрытом каталоге.

Контрольная группа проверяет только указанную последовательность тактик. Ее неуспех не доказывает невозможность автоматического решения средствами Lean. Два повторения небольших известных задач также не устанавливают общее преимущество исследовательского состава.

Следующие разделы описывают прежний вариант 1; он сохранен для воспроизводимости старых отчетов.

## Условия опыта

Команда `cmd/research-compare` выполняет шесть заранее выбранных формальных задач в двух режимах. В одном режиме поиск контрпримеров, выбор метода и формализацию выполняет универсальный профиль. В другом используются отдельные профили доказательства, контрпримеров и формализации. Независимый профиль рецензента одинаков для обоих режимов и не входит в число исследователей.

Конфигурация закрепляет одну модель, один адрес поставщика, цели Lean, ограничения ответов, среду компиляции и навыки. Режимы чередуются по порядку запуска, чтобы первый состав не был всегда одним и тем же. Материалы предыдущего запуска не передаются другому составу.

На ответ установлено 32768 выходных токенов, на попытку 900 секунд. Для собственных исполнителей каждому режиму выделяется не более шести обращений: универсальный профиль до пяти и рецензент до одного; команда до одного для доказательства, одного для контрпримеров, трех для формализации и одного для рецензии. Для внешнего Coddy предусмотрены пределы семь плюс один и один плюс один плюс пять плюс один, то есть по восемь обращений. Смешивать виды исполнителей в одном опыте нельзя.

Равенство пределов не означает равенства фактического расхода. Запросы собственных исполнителей измеряются по событиям. Для Coddy сохраняется верхняя оценка по резерву шагов, если число HTTP-запросов независимо не измерено. Токены, время и неполнота измерения учитываются отдельно. Денежная стоимость не вычисляется.

## Запуск

```sh
go build -o bin/research-compare ./cmd/research-compare
bin/research-compare -config /path/to/private-comparison.json \
  -server-config /path/to/private-server.json \
  -out /path/to/new-private-results -confirm
```

Закрытая конфигурация содержит `cases`, `universal`, `proof`, `counter`, `formalize`, `reviewer`, `lean`. Каждая задача имеет `id` и `goal` с полями `source`, `declaration`, `candidate`; остальные поля используют существующие форматы профиля и среды Lean. Ключи задаются только ссылками на переменные доверенной конфигурации сервера.

Каталог результатов нового опыта должен быть новым. Перед каждым обращением записывается резерв, после обращения сохраняется неизменяемый ответ исполнителя. При остановке процесса неизвестный запрос не повторяется. Резерв прерванного обращения учитывается в общем разрешении на следующие опыты.

Явное продолжение `-resume` проверяет контрольную сумму прежней конфигурации и целей, сохраняет завершенные запуски и переводит прерванный запуск в ошибочный исход без повторения его обращений. Выполняются только еще не начатые пары задачи и режима. Неполное измерение времени и расхода отмечается в отчете. Продолжать измененную конфигурацию в прежнем каталоге нельзя.

## Критерий результата

Вывод исполнителя имеет форму `outcome`, `source`, `evidence`. Исходный файл проверяется против точной цели либо ее отрицания. Положительный промежуточный отчет не засчитывается вместо итоговой проверки. Рецензия получает точные цель, исходник, данные контрпримеров и отчет проверки.

`verified_not_accepted` означает успешную итоговую компиляцию и отсутствие открытого существенного замечания в отчете рецензента, но не приемку оператора. `requires_review` обозначает нерешенное замечание, `inconclusive` отсутствие вывода, `failed` ошибку выполнения, формата или проверки. Эти причины нужно различать при анализе.

Программа аудита проверяет, что объявление цели происходит из доверенного модуля `Goal`, а не создано заново в файле кандидата. В новом отчете `audit_sha256` закрепляет контрольную сумму этой программы; поле не обозначает сумму всего исполняемого проверяющего механизма. При сборке библиотечной леммы цель и доказательство помещаются сервером в один доверенный именованный модуль, который проверяется отдельно.

Старые отчеты без `audit_sha256` сохраняются как исторические данные. Интерфейс отмечает необходимость повторного аудита: прежняя проверка могла принять одноименную подмененную цель при отсутствии импорта `Goal`. Проверка контрольных сумм и повторный запуск той же прежней программы этот пробел не устраняют. Исправленный аудит выполняется отдельно; исходные ответы, отчеты и измерения не переписываются. Новая приемка доказательства или опровержения и новая публикация леммы требуют контрольной суммы актуальной программы аудита. Исторические решения о приемке этим обновлением автоматически не отменяются.

Завершенный отчет записывается оператором через `POST /api/comparisons` с номером снимка, идентификатором команды и подтверждением. Два режима одной задачи должны иметь одинаковую контрольную сумму цели. Таблица доступна в разделе «Исполнители». Она не изменяет статус гипотез и не публикует леммы.

Шесть небольших арифметических задач и один запуск каждого режима не дают общей оценки качества исследовательской команды. Для следующего опыта нужны разные классы задач, повторения, закрепленный набор задач и заранее выбранные показатели. Ошибку формата нельзя объявлять математической ошибкой, а успешную проверку известного тождества новым научным результатом.
