# Проверка и распределение исследовательских задач

## Аудит завершенного опыта

`go run ./cmd/research-audit -dir /path/to/private/comparison` читает отчет сравнения версии 2 и файлы исполнителей. Программа разделяет остановки по времени, ошибки исполнения, отмены, нарушение формы результата и замечания рецензента. Исходные файлы не изменяются; тексты ответов в сводный отчет не копируются. Неизвестный расход сохраняет отдельный признак. Исторический журнал не всегда различает предел ответа и предел шагов; такой случай обозначается `limit_unspecified`.

## Распределение задач

`POST /api/teams` принимает `strategy: "demand"`. Этот режим требует закрепленную цель и проверку Lean. Сначала запускается исследователь с возможностью подготовить исходник. При пригодном исходнике сервер назначает проверку Lean без отдельного формализатора. При отсутствии исходника или ошибке проверки подключается формализатор. Контрпримеры и независимая рецензия обязательны. Профили четырех ролей закрепляются до запуска; пределы попыток и общий бюджет исследования действуют на каждом назначении.

Каждое назначение записывает цель, ее версию, контрольную сумму, роль, метод и выбранные либо отклоненные навыки. Предыдущие ответы передаются как непроверенные материалы; принятые леммы и отчет Lean передаются отдельно. Подмена исходника новым текстом без новой попытки запрещена.

## Рецензия

Новый режим требует форму `proof-review@2`. Замечание содержит `severity`, `category`, `text`, `evidence`, `location`. Категории: постановка, предпосылка, вывод, зависимость, проверка, изложение; в JSON используются `statement`, `premise`, `inference`, `dependency`, `verification`, `exposition`. Существенное замечание или математический вопрос требует основания и места проверки. `editorial` обозначает изложение либо ограничение рецензии. Незакрытые `major` и `question` продолжают блокировать приемку. Сервер не меняет их вид автоматически.

Рецензент без инструментов не обязан повторять вычисление контрольных сумм. Он обязан проверять соответствие естественной постановки формальной цели: успешный Lean не удостоверяет этот переход. Оператор отдельно записывает решение о приемке. Старые формы доступны для исторических записей и прежних порядков работы; новым назначениям `demand` требуется точная версия формы.

## Отдельные проверки Lean

`POST /api/entities/{id}/tactics` с `max_trials: 1..5`, `confirm: true`, снимком и идентификатором команды создает отдельные проверяемые исходники для `simp_all`, `omega`, `ring`, `norm_num`, `aesop`. Каждый исходник имеет свою запись проверки и происхождение `procedure:lean-tactics@1`. Частичное упрощение не останавливает другие проверки. В рабочем API все явно выбранные проверки выполняются независимо; успех одной не отменяет остальные. Максимальная длительность отдельной проверки при закрепленной среде составляет 60 секунд. Модель не вызывается; приемка остается отдельным действием.

`POST /api/lemmas/applications` поддерживает `native_check: true` и `arguments: [{"name":"n","term":"2"}]`. Параметры берутся из нативного описания действующей принятой леммы. Сервер создает исходник применения этой леммы к точному обязательству; Lean проверяет типы, подстановки и оставшиеся предпосылки. Текстовый поиск по описаниям только выбирает кандидатов. Неудачная проверка не доказывает невозможность применения: может потребоваться другая подстановка или отдельная лемма. Автоматического поиска всех подстановок пока нет.

## Условия навыков

Версия навыка может содержать `contract.applicability`: роли, разрешенные методы, требование формальной цели, проверенного кандидата, принятых оснований и минимального остатка попыток. При назначении внутри команды эти условия проверяются по состоянию сервера. Процедура навыка не расширяет список инструментов профиля. Математические условия, выраженные естественным языком, остаются обязательствами доказательства; сервер не считает их истинными из-за наличия текста в навыке. Для отдельных заданий вне команды автоматический отбор по этим условиям пока не применяется.

## Учебное исследование

`POST /api/research-pilots` с `recipe: "injective-iterations@1"` создает известную постановку: левое обратное отображение обеспечивает инъективность каждой итерации. Разбиение включает инъективность из левого обратного, композицию, индукцию по числу итераций и обязательство перехода к исходной цели. Альтернативное задание проверяет прямое доказательство средствами Mathlib. Отдельная проверка границ рассматривает правое обратное; это измененная постановка, а не контрпример к исходной цели.

`route: "direct"` создает отдельное исследование той же формальной цели без обязательного разбиения; по умолчанию действует `decomposed`. Выбор прямого варианта не удаляет основания уже созданного исследования. В интерфейсе вариант выбирается до создания.

Создание допускается при общей приостановке и не вызывает модель. `/api/studies/{id}/proof-progress` возвращает состояния, действующие проверки, основания, незакрытые замечания и доступные модули. Веб-интерфейс показывает эти данные в разделе заданий. Успешные местные проверки доказывают конкретные формальные утверждения; они не устанавливают преимущества команды над одним агентом и не принимают результат автоматически.
