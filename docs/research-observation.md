# Управление поиском и наблюдение

## Разбор сравнения

```sh
go run ./cmd/research-summary -report /private/comparison/report.json \
  -analysis -artifacts-dir /private/comparison \
  -out /private/new-analysis.json
```

Каталог материалов нужен для разбора замечаний рецензента. Программа проверяет сумму каждого прочитанного `result.json` по записи соответствующего этапа. Несовпадающий или отсутствующий файл не используется. Ответ с совпадающей суммой, но неверной структурой отмечается как `bound_invalid_contract`; это не математическое возражение.

Разбор содержит данные по классам и задачам, разницу долей проверенных результатов, числа обращений и времени относительно одного исследователя. Повторения сначала усредняются внутри задачи; они не считаются независимыми задачами. Неполные и отмененные группы не входят в парное сопоставление. При незавершенном опыте вывод содержит `preliminary: true`. Данные описательные: программа не строит доверительных интервалов и не утверждает общего преимущества режима.

API оператора: `GET /api/evaluations/{id}/analysis` для наблюдаемого файла и `GET /api/comparisons/{id}/analysis` для сохраненного отчета. Второй маршрут не читает местные файлы рецензий.

## Состояние процесса

Для новых запусков `research-compare` поддерживает `-progress-file /private/comparison/progress.json`. Родительский каталог должен существовать с правами 0700. Файл содержит обозначения задачи, режима, роли, стадии, времени последнего события и отдельного подтверждения работы процесса. Постановки, ответы, аргументы инструментов, ключи и внутренние рассуждения не записываются. Подтверждение работы обновляется каждые пять секунд; оно не означает продвижения исследования.

В закрытой записи `evaluations` можно указать `progress_file`, `process_file` и `stale_seconds` (60..3600, по умолчанию 1200). `process_file` имеет ту же структуру наблюдения и предназначен для отдельного наблюдателя службы. Он должен содержать точную `configuration_sha256`, `observed_at` и `process_state`: `running`, `stopped`, `failed` или `completed`. Записи старше 45 секунд не подтверждают текущее состояние процесса. Все файлы находятся вне веб-каталога.

Интерфейс различает остановленный процесс, давно не обновленный отчет и последнюю известную стадию. Для старого запуска без записи стадий показывается только последняя контрольная запись. Добавление наблюдателя не требует перезапуска опыта. Наблюдатель не назначает попытки и не повторяет запросы с неизвестным исходом.

## Доставка итогов

```sh
go run ./cmd/research-finalize \
  -report /private/comparison/report.json \
  -out /private/comparison-delivery \
  -server http://127.0.0.1:4187 \
  -token-env RESEARCH_API_TOKEN \
  -configuration-sha256 APPROVED_CONFIGURATION_SHA256 \
  -watch
```

Ключ передается через указанную переменную окружения, не через аргумент команды. Допускается HTTPS либо HTTP с числовым адресом обратной петли. Программа не обращается к модели. Она ожидает полного отчета, сохраняет отчет, сводку и разбор в закрытом каталоге, затем доставляет отчет через API. Приемка математических утверждений не выполняется.

Перед отправкой сохраняются точные тело запроса, его сумма и стабильный идентификатор. После потери подтверждения программа сначала ищет отчет по сумме в рабочей базе. Если запись уже есть, повторная отправка не выполняется. Если записи нет, повторяется только сохраненный запрос доставки, а не исследование. Известный конфликт версии позволяет подготовить новую версию после повторного чтения состояния. Файл `delivery.json` сохраняет состояние доставки. После перезапуска используется прежний каталог назначения.

## Ограниченные решения по ветви

`POST /api/branches/{id}/policy` требует подтверждения оператора, версии состояния и идентификатора команды. Поля `policy`: `enabled`, `mode` (`observe` или `execute`), `methods`, `failure_threshold` (1..5), `max_decisions` (1..5). Начальный режим интерфейса только наблюдает. Рекомендации доступны через `GET /api/branches/recommendations?study=ID`.

Исполнение требует конечного общего бюджета попыток и обращений. Правила могут остановить ветвь, запросить отдельный план или создать связанную ветвь с другим разрешенным приемом. Число решений и список использованных приемов сохраняются при замене ветви. Общий бюджет не сбрасывается. Ручное удержание, общая пауза, активная попытка и неизвестный расход блокируют автоматическое назначение. Решение записывается с `actor: policy` и суммой утвержденных правил.

Предел технических неуспехов служит основанием организационного решения, но не доказывает непригодность приема. Успешная местная проверка останавливает дальнейший поиск до рецензии. Приемка и включение модулей в библиотеку остаются отдельными действиями.

## Связи памяти

`GET /api/memory/suggestions?target=ID` лексически подбирает записи других утверждений того же исследования. Ответ показывает различия постановок, условий, формальных целей и обязательных модулей. Все такие подсказки имеют `auto_reuse: false`, включая технические неуспехи.

`POST /api/memory/relations` принимает `memory`, `target`, формальную `goal`, пояснение `note`, `confirm`, `expected_revision`, `request_id`. Он создает отдельное обязательство с заданной оператором формальной связью.

Обязательство наследует действующие принятые модули из сред связанных целей: до шестнадцати модулей и оснований. Модули доступны для импорта, но использование каждого из них в терме не обязательно; поле `required_libraries` этим действием не задается. Непроверенные исходная и целевая гипотезы не становятся его предпосылками.

Проверка этой связи не устанавливает эквивалентность текстовых условий и не переносит технический исход между задачами. Изменение исходной цели, целевой цели или цели обязательства делает связь устаревшей. Даже проверенная связь сама по себе не принимает исходную гипотезу.

## Смена представления

`POST /api/experiments/representation` выполняет до четырех местных проверок без модели: ограниченный поиск исходной цели, поиск преобразованной цели, проверку эквивалентности и перенос доказательства обратно. Нужен действующий модуль принятой леммы. Исходная цель, преобразованная цель и эквивалентность должны быть разными объявлениями в одном неизменном исходнике `Goal.lean`.

Запрос содержит `target`, `library`, `direct`, `bridge`, `bridge_source`, `bridge_author`, `depth` (1..6), `timeout_seconds` (1..120 на проверку), подтверждение и реквизиты команды. Lean отдельно проверяет, что тип `bridge` определительно равен `direct ↔ original`. Переданный оператором исходник эквивалентности проверяется с указанием авторства. Итоговый кандидат повторно проверяется против точной исходной цели. Непройденный поиск означает только неуспех заданной процедуры в ее пределах.

Отчет сохраняется в базе и `inspections/{id}/report.json`; исходники и отчеты отдельных проверок находятся рядом. Применение кандидата, рецензия и приемка не входят в опыт.
