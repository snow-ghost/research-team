# Адаптивный цикл и версии навыков

## Автоматическое доказательство и отрицание

Сервер формирует `Goal.lean` из закрепленной версии постановки, а `Candidate.template.lean` содержит `import Goal` и полное имя теоремы-кандидата. Эти файлы входят в контрольную сумму пакета попытки. Шаблон не содержит завершенного доказательства. Сервер не вставляет недостающие команды в ответ модели.

При отсутствии завершенного блока Lean координатор назначает отдельную попытку исправления формы ответа. Ошибка итоговой проверки передается формализатору вместе с предыдущим материалом. Исходные ответы и отчеты сохраняются без редактирования. Каждое исправление расходует попытку и резерв исследования; координатор оставляет попытку для последующей рецензии.

Найденный контрпример может быть передан формализатору для доказательства `Not` исходной постановки. Неуспешная проверка отрицания допускает ограниченное исправление, но не означает, что исходная цель доказана. Рецензия связывается с фактическим автором последней проверенной версии. Приемка доказательства и опровержения остается отдельным решением оператора.

## Порядок работы

`POST /api/teams` принимает `strategy`:

| Значение | Порядок |
|---|---|
| `fixed` или пустое | Доказательство и контрпримеры назначаются вместе, затем формализация и рецензия |
| `adaptive` | Сначала контрпримеры; отрицательный кандидат передается формализатору, в остальных случаях назначается поиск доказательства |

Адаптивный режим требует проверки Lean. Параметр `methods` задает список различных приемов из `GET /api/research-methods`. При неуспешной проверке положительного доказательства выбирается следующий разрешенный прием. После исчерпания списка используется последний прием до исчерпания бюджета. Диагностика формы ответа не считается математическим основанием для смены метода.

Предыдущие материалы передаются в контексте команды как непроверенные. Отчеты Lean имеют отдельную привязку к постановке и исходнику. Принятие цели прекращает связанные задачи через существующий механизм отмены. Изменение постановки блокирует продолжение прежней версии.

Этот порядок не выбирает произвольные новые гипотезы и не оптимизирует бюджет по обучаемой оценке полезности. Дерево обязательств, предел исследования и разрешенные методы задаются явно.

## Каталог навыков

`POST /api/skills` создает неизменяемую версию навыка `name@N`. Запись содержит инструкции, условия применения, входные данные, формат результата, необходимые инструменты, критерии остановки и примеры. Контрольная сумма закрепляет весь состав версии. Изменение процедуры создает следующую запись, сохраняя прежнюю.

```json
{
  "expected_revision": 12,
  "request_id": "skill-example-1",
  "name": "formal-proof",
  "label": "Формализация",
  "instructions": "Докажи импортированную постановку и проверь предпосылки.",
  "contract": {
    "preconditions": ["Закрепленная цель Lean"],
    "inputs": ["Постановка", "Проверенные основания"],
    "output": "Один завершенный блок Lean",
    "required_tools": ["check_lean"],
    "stop_criteria": ["Получено доказательство или исчерпан предел"],
    "examples": ["Известное тождество с натуральным параметром"]
  },
  "confirm": true
}
```

При создании профиля `POST /api/profiles` поле `skill_refs` закрепляет точные версии. Одновременно передавать ссылки и встроенный список `skills` нельзя. Требуемые инструменты должны уже входить в разрешения профиля; требования навыка не изменяют их. Профиль сохраняет копию выбранных версий и собственную контрольную сумму, а попытка закрепляет эту конфигурацию.

Контракт передается модели как данные задания. Программа проверяет форму записи и разрешения инструментов. Она не проверяет смысл произвольных текстовых условий и не гарантирует их исполнение моделью. Итоговая проверка Lean и независимая рецензия остаются необходимыми.

## Структура леммы

`POST /api/lemmas/inspect` принимает `library`, `domain`, `expected_revision` и `request_id`. Сервер проверяет действительность принятой библиотечной версии и суммы ее файлов, затем извлекает структуру средствами Lean. Операция ограничена 60 секундами и учитывается среди работающих нативных проверок.

Отчет сохраняет параметры, экземпляры классов типов, предпосылки, заключение, параметры универсумов, полный тип и суммы постановки, модуля, окружения и программы извлечения. Поле `domain` задается оператором. Оно не выводится из Lean автоматически.

Ручное описание через `/api/lemmas/signatures` остается доступным, но не может содержать нативный отчет. Интерфейс различает источники «Lean» и «Оператор». Поиск использует нормализованные строки типов и условий; унификация, доказательство эквивалентности типов и автоматический подбор термов подстановки не реализованы. Предложенное применение создает отдельное обязательство, которое должно пройти Lean и приемку.
