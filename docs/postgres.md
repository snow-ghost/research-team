# PostgreSQL и исследовательский цикл

## Запуск

PostgreSQL работает в Docker Compose, Go-сервер работает на хосте. Нужны Linux, Docker с Compose, Go 1.26 и Node.js 24 для сборки интерфейса.

Команды из корня репозитория:

```sh
go run ./cmd/research-db -init-local
docker compose --env-file .env.postgres up -d postgres
docker compose --env-file .env.postgres ps
cd web-research-demo
npm ci
npm run build
cd ..
./scripts/run-postgres.sh
```

Первая команда создает `.env.postgres` с правами `0600` и случайными паролями. Существующий файл она не перезаписывает. Файл исключен из Git. Значения паролей в журнал не выводятся.

Веб-интерфейс: http://127.0.0.1:4187/. Ключ входа находится в `.research-server/access-token`. Порт PostgreSQL привязан к `127.0.0.1:55433`. При занятом порте измените и `POSTGRES_PORT`, и порт в `RESEARCH_DATABASE_URL` внутри закрытого файла.

Для ограничения опубликованного порта локальным адресом используйте Docker Engine 28 или новее. В версиях до 28.0.0 другие узлы того же сетевого сегмента могут достигать такого порта; это [известное ограничение Docker](https://docs.docker.com/engine/network/port-publishing/). На 24 сентября 2026 года в рабочей среде установлен Docker Engine 29.8.1, поэтому указанное ограничение старых версий к ней не относится. PostgreSQL требует пароль независимо от привязки порта.

Конфигурация сервера: [examples/server/postgres.json](../examples/server/postgres.json). Соединение задается через `database.driver=postgres` и имя переменной `database.dsn_env`. При недоступности PostgreSQL сервер не переключается на SQLite.

Compose создает отдельные сеть и том `research-team_postgres_data`. Приложение подключается ролью `research`, которая владеет своей базой, но не имеет прав суперпользователя, создания баз или ролей. Административный пароль используется при начальной настройке контейнера. Образ закреплен по версии и контрольной сумме.

Не выполняйте `docker compose down -v` для рабочей базы: параметр `-v` удаляет том. Изменение пароля в файле окружения не меняет пароль уже созданной роли; для смены нужен отдельный административный запрос.

## Перенос SQLite

Сначала остановите прежний Go-сервер и сделайте закрытую резервную копию всего `data_dir`. PostgreSQL должен быть пуст, а `data_dir` должен указывать на прежнюю рабочую область с `research.db` и каталогом `attempts`.

```sh
set -a
. ./.env.postgres
set +a
go run ./cmd/research-db -config examples/server/postgres.json -import-sqlite
./scripts/run-postgres.sh
```

Команда применяет миграции и переносит текущее состояние, всю историю и идентификаторы обработанных команд в одной транзакции. История проверяется на непрерывность и соответствие текущему состоянию. Повторный перенос в непустую или ранее импортированную базу отклоняется.

Исходная SQLite открывается только для чтения и не удаляется. Файлы попыток, материалы Coddy и ключ входа остаются в прежнем каталоге. Перенос в другой `data_dir` этой командой не поддерживается.

После переключения прежняя SQLite остается архивным снимком. Последующие изменения PostgreSQL в нее не копируются. Для возврата к прежней версии необходимо отдельно согласовать восстановление базы и файлов.

Для новой пустой рабочей области импорт не нужен. Проверить и применить миграции без запуска исполнителей можно командой:

```sh
go run ./cmd/research-db -config examples/server/postgres.json
```

## Схема

| Объекты | Хранение |
|---|---|
| Исследования и утверждения | `studies`, `entities` |
| Основания и ветви работы | `dependencies`, `work_links` |
| Задания и попытки | `tasks`, `attempts` |
| Вопросы, замечания и применения | `questions`, `findings`, `applications` |
| Решения о приемке | `review_decisions` |
| Делегирование Coddy и циклы | `delegations`, `research_cycles` |
| Проверки, команды и результаты | `proof_verifications`, `research_teams`, `research_results` |
| Разбиения и библиотека | `decomposition_proposals`, `lemma_library` |
| События и версии | `events`, `object_versions`; представление `entity_versions` |
| Повторные команды и перенос | `commands`, `imports` |
| Версия рабочей области и миграции | `workspace`, `schema_migrations` |

Предметные записи содержат JSONB и вычисляемые типизированные столбцы для связей и отбора. Внешние ключи проверяют существование исследований, целей, заданий и оснований. Индексы поддерживают поиск по исследованию, состоянию и зависимости. Таблица `dependencies` отдельно фиксирует требуемую версию основания.

История записывает только изменившиеся объекты. Снимок на указанную ревизию собирается из последних версий объектов до этой ревизии. Изменение текущих записей, исторических версий, решения и идентификатора команды фиксируется одной транзакцией.

Миграции находятся в `internal/researchweb/migrations/` и включены в Go-программу. Примененные файлы проверяются по контрольной сумме; более новая версия схемы или поврежденная история миграций блокирует запуск. Изменять примененную миграцию нельзя: добавляйте следующую.

Сервер сохраняет ограничение одного координатора на базу. Его обеспечивает блокировка PostgreSQL на время соединения; закрытый каталог файлов дополнительно защищен блокировкой ОС. Потеря доступа к базе останавливает координацию. Это не распределенная очередь исполнителей.

Предметная логика пока читает рабочую область целиком и использует общую ревизию для защиты от конфликтов. Пределы 16 МиБ состояния, 2000 утверждений, 100 попыток и 100 циклов сохранены. Архивирование, постраничный API и испытания больших исследований остаются отдельными задачами.

## Минимальный Цикл

В разделе заданий доступен запуск цикла. Оператор выбирает исследование, профиль исполнителя, каталог материалов и предел от 1 до 20 попыток. Отдельное подтверждение разрешает автоматические запуски в этих пределах.

1. Координатор обходит заданные зависимости от цели к незакрытым основаниям.
2. Для обязательства с принятыми основаниями создает задание и попытку, сразу учитывая ее в пределе.
3. Исполнитель получает снимок, текущие основания и замечания предыдущей рецензии.
4. Проверенный по происхождению кандидат присоединяется к неизменившейся версии и направляется на приемку.
5. После решения оператора координатор переходит к следующему обязательству или создает задание исправления.
6. При принятой общей цели цикл завершается и сохраняет номер снимка приемки.

Пауза цикла запрещает создание новых заданий и запуск его попыток из очереди. Уже начатая подготовка материалов или исполнение продолжаются. Остановка отменяет его незавершенные попытки. Продолжение после паузы требует подтверждения. Исчерпание попыток, ошибка исполнителя или недействительные основания прекращают автоматическое продвижение.

После перезапуска незавершенные циклы отмечаются прерванными. Оператор проверяет результаты и отдельно разрешает новый цикл. Автоматического повтора внешнего действия с неизвестным исходом нет.

Завершение относится к зафиксированному историческому снимку. Последующее оспаривание леммы не запускает новые оплачиваемые попытки автоматически.

Это цикл по заданному оператором дереву с одним профилем исполнения на цикл. Автоматическая генерация новых гипотез, выбор между разными доказательными приемами и периодический агент улучшения оценки пока не реализованы. Число попыток ограничивает исполнения, но не заменяет общий денежный бюджет. Приемку выполняет оператор; формальной проверки математики нет.

API: `POST /api/cycles` и `POST /api/cycles/{id}/commands`. Команды управления: `pause`, `resume`, `stop`. Они требуют `expected_revision` и `request_id`; запуск и продолжение дополнительно требуют `confirm=true`.

## Резервная Копия

Остановите сервер, затем сохраните базу и каталог материалов одной согласованной парой. Для автоматического сравнения таблиц и файлов после восстановления используйте [research-backup](research-branches-memory.md#postgresql-и-резервная-копия). Ручной пример ниже не выполняет такого сравнения и включает ключ входа:

```sh
umask 077
mkdir -p .research-server/backups
docker compose --env-file .env.postgres exec -T postgres \
  pg_dump -U postgres -d research -Fc > .research-server/backups/research.dump
tar --exclude='./backups' -czf .research-server/backups/materials.tar.gz \
  -C .research-server .
```

Копии содержат исследовательские данные и ключ входа. Храните их вне публичного репозитория. Для нескольких копий используйте разные имена; команды выше перезаписывают указанные файлы.

Проверять восстановление следует в отдельной пустой базе:

```sh
docker compose --env-file .env.postgres exec -T postgres \
  createdb -U postgres -O research research_restore
docker compose --env-file .env.postgres exec -T postgres \
  pg_restore -U postgres --role=research --no-owner --exit-on-error \
  -d research_restore < .research-server/backups/research.dump
```

Для запуска восстановленной области нужны соответствующие файлы материалов и строка соединения с `research_restore`. Не направляйте два сервера с разными базами на один каталог файлов. Восстановление базы без файлов не восстанавливает результаты попыток.

Проверка восстановления тестовой базы автоматизирована:

```sh
node scripts/check-postgres-backup.mjs research_web_test
```

Сценарий создает отдельную случайно именованную базу, восстанавливает выгрузку, сравнивает число строк и контрольные суммы содержимого всех таблиц, затем удаляет только созданную им базу. Исходная база должна быть остановлена с точки зрения записи; ее изменение во время проверки вызывает отказ. Рабочие базы без окончания `_test` не принимаются.

## Проверки

Быстрые проверки работают с SQLite. Для PostgreSQL создайте отдельную тестовую базу:

```sh
docker compose --env-file .env.postgres exec -T postgres \
  createdb -U postgres -O research research_test
export RESEARCH_TEST_POSTGRES_DSN="postgres://research:${RESEARCH_DB_PASSWORD}@127.0.0.1:${POSTGRES_PORT}/research_test?sslmode=disable"
go test -race ./...
```

Загрузите `.env.postgres` в окружение перед этими командами. Проверки PostgreSQL создают и удаляют собственные случайные схемы, требуют имя базы с окончанием `_test` и не обращаются к рабочей базе.

Для браузерного прогона `MVP_DATABASE_URL` указывает на отдельную пустую базу с окончанием `_test`. Без этой переменной используется временная SQLite. Пример настройки базы:

```sh
docker compose --env-file .env.postgres exec -T postgres \
  createdb -U postgres -O research research_web_test
export MVP_DATABASE_URL="postgres://research:${RESEARCH_DB_PASSWORD}@127.0.0.1:${POSTGRES_PORT}/research_web_test?sslmode=disable"
cd web-research-demo
npm run test:mvp
```

Повторный браузерный прогон требует новой пустой базы. Модель и GitHub в испытании заменены местными ответами; оплачиваемые обращения не выполняются. GitHub Actions поднимает PostgreSQL отдельно для Go и браузерных проверок.

Технические основания: [официальный образ PostgreSQL](https://hub.docker.com/_/postgres), [блокировки PostgreSQL](https://www.postgresql.org/docs/18/explicit-locking.html), [драйвер pgx](https://github.com/jackc/pgx).
