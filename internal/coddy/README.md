# Соединитель полного процесса Coddy

Модуль связывает исследовательское задание с задачей GitHub, обработкой Coddy и запросом на слияние. Сам Coddy работает отдельной службой. Модуль не заменяет его внутреннего агента прямым ACP-клиентом.

Состояние сохраняется локально в закрытом каталоге. Реализация рассчитана на одного владельца этого каталога под Linux; это не распределенная очередь.

## Подготовка

1. Настроить отдельный репозиторий и учетную запись Coddy по [инструкции развертывания](../../integrations/coddy/README.md).
2. Задать параметры в [connector.json](../../examples/coddy/connector.json): репозиторий, учетную запись Coddy и отдельную учетную запись исследовательского координатора.
3. Предоставить процессу `RESEARCH_GITHUB_TOKEN` через защищенное окружение. Токен не входит в JSON. Текущая версия проверяет владельца через `GET /user` и рассчитана на пользовательский токен; токен установки GitHub App не поддержан этим способом проверки.
4. Указать точный исходный хеш в [job.json](../../examples/coddy/job.json) вместо нулевого значения из примера.

У учетной записи координатора нужны права чтения содержимого и записи задач и запросов на слияние в выбранном репозитории. Она должна иметь право назначать задачу учетной записи Coddy. Публикация в открытый репозиторий запрещена по умолчанию; для нее требуется отдельное `allow_public_repository: true`.

Проверить конфигурацию без чтения токена и без сети:

```sh
go run ./cmd/research-coddy -config examples/coddy/connector.json
```

Подготовить запись без публикации:

```sh
go run ./cmd/research-coddy \
  -config examples/coddy/connector.json \
  -state-dir .research-coddy \
  -action prepare -job examples/coddy/job.json
```

Команда возвращает `id` делегирования. Один и тот же `attempt_id` в одном репозитории дает тот же идентификатор. Изменение задания или конфигурации при повторной подготовке отклоняется. Каталог содержит исходные материалы; его нельзя публиковать в Git.

## Команды

Все команды ниже используют тот же `-config` и `-state-dir`. Идентификаторы и хеши берутся из вывода предыдущих команд.

| Действие | Дополнительные параметры | Результат |
|---|---|---|
| `local` | `-id` | Чтение локальной записи без сети |
| `submit` | `-id -publish` | Создание задачи с назначением Coddy |
| `observe` | `-id` | Получение задачи, комментариев, связанного запроса на слияние и рецензий |
| `approve-plan` | `-id -request-id -target issue\|pr -comment-id -expected-view -publish` | Подтверждение выбранного плана Coddy |
| `reply` | `-id -request-id -target issue\|pr -message -expected-view -publish` | Ответ или уточнение без фразы подтверждения |
| `request-changes` | `-id -request-id -review -expected-view -publish` | Рецензия с замечаниями к строкам файлов |
| `collect` | `-id -expected-view` | Сохранение материалов кандидата |
| `reconcile` | `-id` | Сверка неопределенного исхода без повторного внешнего действия |
| `hold` | `-id` | Запрет новых действий этого соединителя |
| `resume` | `-id` | Снятие местного запрета оператором |

`expected-view` равен `last_observation.digest` из `observe`. `request-id` задается оператором один раз для намерения и сохраняется при повторе команды. Другой текст с тем же идентификатором отклоняется. Повтор того же намерения под новым идентификатором также отклоняется.

Пример публикации после проверки задания:

```sh
go run ./cmd/research-coddy \
  -config examples/coddy/connector.json \
  -state-dir .research-coddy \
  -action submit -id "$DELEGATION_ID" -publish
```

`-publish` разрешает конкретное внешнее действие. Назначение задачи уже запускает подготовку плана и может вызвать расходы модели. Подтверждение плана означает разрешение Coddy изменять программу, отправлять изменения и создавать запрос на слияние. Отдельного запрета отправки изменений после подтверждения штатный цикл Coddy не обеспечивает.

`reply` читает JSON с полем `body`. Фразы, которые Coddy трактует как подтверждение, отклоняются, включая их употребление в отрицательном предложении. Для подтверждения используется `approve-plan`. Для новых требований без согласования можно передать, например, `{"body":"Нужно отдельно рассмотреть n=1."}`.

После уточнения Coddy может опубликовать запрос продолжения `Data is sufficient. Shall I proceed...`. Он также требует явного `approve-plan` с идентификатором этого комментария и новым снимком.

Рецензия описывается в [review.json](../../examples/coddy/review.json). Нужны общий текст и хотя бы одно замечание к строке измененного файла. Поддержана сторона `RIGHT`, поскольку изученный обработчик Coddy использует ее при передаче замечаний агенту. Общая рецензия без строк не запускает этот цикл.

## Сверка после сбоя

Перед `POST` сохраняются точное намерение, его идентификатор, тело и целевой объект. При потере ответа операция остается `unknown`, дальнейшие записи блокируются.

`reconcile` читает объекты GitHub и проверяет тело, автора, идентификатор попытки и привязку. Один подходящий объект подтверждает операцию; несколько требуют разбора оператором. Отсутствие объекта, неполная выборка и превышение предела страниц не разрешают автоматический повтор.

Даже отказ `POST` с кодом HTTP сохраняется консервативно как неизвестный исход. Автоматическое снятие этого состояния после доказанного отказа пока не реализовано. Создание новой попытки после такого случая требует проверки внешнего состояния оператором; удалять или править журнал для повторной отправки нельзя.

Блокировка каталога предотвращает одновременную запись двумя местными процессами. Копирование каталога и работа из двух независимых копий нарушают это условие.

Один ответ GitHub ограничен 2 МиБ, накопленная выборка одного списка 8 МиБ, файл состояния 32 МиБ. Превышение предела возвращает ошибку без усечения материала до частичного успеха.

## Связь результата

Внешний заголовок задачи имеет вид `research-<идентификатор>`. Человекочитаемое название и весь контракт находятся в описании. Это дает однозначное имя ветви для закрепленного правила Coddy.

Запрос на слияние проверяется по репозиторию, точной ветви, целевой ветви и учетной записи Coddy. Совпадения текста описания недостаточно. Несколько совпадающих запросов считаются неоднозначностью.

`collect` сохраняет `candidate-<sha256>.json`: задание, снимок GitHub, точные хеши, перечень измененных файлов и доступные части различий. Повторное чтение проверяет, что снимок не изменился во время сбора. Пустой или неполный перечень файлов отклоняется.

Материал получает только `status: candidate`. Полный исходный код не скачивается, испытания не выполняются, корректность построения от исходного хеша помечается `unverified`. Фрагменты различий GitHub могут отсутствовать или быть неполными. Для воспроизводимой проверки нужна отдельная загрузка закрепленной версии и запуск проверяющей среды.

## Ограничения

- Coddy и его агенты запускаются и останавливаются внешней службой управления процессами. `hold` не останавливает их, не отзывает уже переданное согласие и не блокирует наблюдателя Coddy.
- Чтение нескольких ресурсов GitHub не является атомарным снимком. Проверка `expected-view` обнаруживает уже видимое изменение, но не устраняет гонку между последним чтением и публикацией согласия. Для строгого согласования требуется изменение протокола Coddy.
- Исходная ветвь проверяется перед созданием задачи и подтверждением первого плана. Она может измениться позже. Соответствие результата исходной версии все равно требует проверки.
- Состояния `waiting_for_coddy` и `pull_request_open` показывают наблюдаемое состояние GitHub; они не подтверждают, что процесс Coddy работает.
- Соединитель не управляет внутренним бюджетом, повторениями, разрешениями ACP или данными `.coddy`.
- Код Coddy самостоятельно принимает комментарии других участников. Ограничения соединителя не распространяются на прямые действия в GitHub.
- Слияние, автоматическая приемка, постоянная фоновая служба наблюдения и веб-управление пока отсутствуют. `observe` выполняет один опрос.
- Секреты не записываются соединителем, но исходные материалы и полученные комментарии могут содержать чувствительные данные. Нужны закрытый каталог состояния и проверка состава публикации.

## Проверки

```sh
go test -race ./...
go vet ./...
CODDY_SOURCE=/path/to/pinned/coddy python3 integrations/coddy/test_review_patch.py
```

Go-проверки используют местный HTTP-сервер. Проверка поправки исполняет извлеченную функцию Coddy с подставными агентом, Git и GitHub. Реальная учетная запись и модель не использовались.
