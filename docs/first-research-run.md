# Подготовка первого исследования

## Предварительная Проверка

Команда читает настройки нашей системы и выполняет только `coddy --version` в отдельном временном домашнем каталоге:

```sh
go run ./cmd/research-preflight -config examples/server/postgres.json
```

Можно явно указать файл через `-coddy /путь/к/coddy`. Команда не запускает попытку, не обращается к модели, не читает ключ из личного каталога Coddy и не меняет конфигурацию. Вывод JSON содержит `ready`, `model_called` и результаты отдельных проверок.

Код завершения программы `2` означает, что местные условия запуска не выполнены. `go run` дополнительно печатает `exit status 2` и может сам завершиться кодом `1`.

Проверяются версия, соответствие установленного и настроенного файла, наличие профиля, замена значений примера, доступность ключей через серверный источник учетных данных, разрешение внешнего исполнения и существование каталогов материалов. Если задан `secret_file`, проверка читает его, но не выводит значения и не передает их программе проверки версии.

`scope=local_configuration_only`: даже `ready=true` не подтверждает доступность провайдера, оплату, работу PostgreSQL, изоляцию процесса или качество ответа модели. Эти проверки выполняются отдельно. Полный денежный бюджет еще не реализован.

## Coddy

Адаптер допускает Coddy Agent `1.1.64`, `1.2.1` и `1.2.54`. Профиль закрепляет одну точную версию. Для другой версии сначала нужны проверка протокола и разрешений, испытание настоящего файла с местной подставной моделью и обновление адаптера.

Сервер использует собственный профиль, а попытка получает отдельный временный домашний каталог. Личные сеансы, память, правила и навыки не импортируются. Ключ подключается только отдельной командой подготовки по решению оператора.

Флаг `allow_external_execution` разрешает запуск, но сам не создает изоляцию. Для Coddy реализовано `execution_boundary=docker`: закрепленный локальный образ, запуск от пользователя сервера, корневая файловая система только для чтения, удаленные дополнительные возможности ядра, ограничение памяти, процессоров и числа процессов. В контейнер передаются только файл Coddy, копия материалов только для чтения и временный каталог попытки. Сокет Docker и домашний каталог оператора не передаются.

Сеть контейнера доступна для модели и поиска. Ограничение исходящих адресов пока не реализовано. Процесс сервера имеет доступ к Docker; администратор Docker входит в доверенную границу и может видеть окружение контейнера. Ключ передается через окружение, без значения в аргументах команды и конфигурации агента. Удаление контейнера выполняется отдельно от остановки подключенного процесса Docker.

Режим Coddy закреплен как `ask`. Запись исходников, оболочка и вложенные агенты запрещены. Агент возвращает текст кандидата; отдельная [проверяющая служба Lean](research-workflow.md) компилирует его и возвращает диагностику формализатору.

## Подготовка Закрытого Профиля

Команды выполняются из корня проекта после сборки веб-интерфейса и настройки PostgreSQL по основной инструкции. Требуются Linux, Docker BuildKit, статический исполняемый файл Coddy 1.2.54 и существующий вход NeuralDeep в Coddy. Сборка использует только публичный набор корневых сертификатов указанной машины; его содержимое влияет на идентификатор образа.

```sh
docker build --build-context ca-bundle=/etc/ssl/certs -t research-team-coddy:local deploy/coddy
go run ./cmd/research-prepare-coddy -image "$(docker image inspect research-team-coddy:local --format '{{.Id}}')"
go run ./cmd/research-preflight -config .research-server/coddy-launch/server.json -coddy "$HOME/.local/bin/coddy"
```

Команда подготовки читает выбранного провайдера и модель из `~/.coddy/config.yaml`. Импорт поддерживает только сохраненный вход NeuralDeep без встроенного `api_key` и проверяет соответствие адреса API адресу выдачи ключа. Для других провайдеров профиль настраивается отдельно через существующее сопоставление переменных окружения.

По умолчанию команда закрепляет `1.2.54`; для ранее проверенной установки `1.2.1` можно явно задать `-version 1.2.1`. Перед заменой установленного файла проверяются контрольная сумма официального выпуска и настоящий файл на местной подставной модели. Действующий профиль сервера обновляется вместе с версией установленного файла.

Файлы `profile.json`, `server.json` и `secrets.json` создаются с правами `0600` в `.research-server/coddy-launch` с правами `0700`. Повторное выполнение не перезаписывает существующий каталог. Сервер отклоняет общедоступный файл ключей, ссылку вместо файла или размещение в каталоге веб-интерфейса. Каталог исключен из Git; все три файла являются локальными настройками.

Личная установка Coddy и исходная конфигурация сервера остаются без изменений. Новая конфигурация включает только подготовленный профиль и материалы задачи; соединитель Coddy Bot в ней выключен. Команда подготовки не обращается к модели.

Запуск сервера, когда его порт свободен:

```sh
sh scripts/run-postgres.sh -config .research-server/coddy-launch/server.json
```

Адрес: `http://127.0.0.1:4187`. Сохраняется прежний каталог состояния и ключ входа.

## Выбранная Задача

[Материалы](../examples/research/wide-kernel/TASK.md): у матрицы над полем с числом столбцов больше числа строк существует ненулевой вектор ядра.

Источник: `exists_nonzero_mulVec_zero` в проекте FinEqs, включенном в [lean-pool](https://github.com/Vilin97/lean-pool/blob/91d0ec39f64373612c106504fcd164451c460c38/LeanPool/Fineqs/Main.lean). Авторы исходного файла: Stefan Baranczuk и Aristotle; исходная лицензия Apache-2.0. Формальная постановка в наших материалах записана отдельно; исходное доказательство не скопировано.

Это известный результат с опубликованным решением. Он подходит для проверки работы системы, но не для оценки математической новизны. Текущие открытые задачи `Challenge/` требуют значительно большего объема формализации.

- `Goal.lean`: определение формального утверждения, без доказательства и без `sorry`.
- `TASK.md`: условия и требуемый результат.
- `study.json`: поля создания исследования.
- `source.json`: источник, версии и границы опыта.

В запросе `POST /api/actions` к полям `study.json` нужно добавить текущую `expected_revision` и новый `request_id`. Файл сам по себе не является готовым авторизованным запросом.

Подготовленный профиль регистрирует `examples/research/wide-kernel` как каталог материалов. Сервер создает его снимок для попытки. В нем находятся постановка и сведения о публичном происхождении задачи; файлов настройки и ключей нет. Публичность исходного решения не позволяет оценивать независимость открытия по одному ответу модели.

## Проверка Lean

Короткий пример без mathlib:

```sh
lean examples/research/lean/FirstProof.lean
```

Ожидается сообщение об отсутствии аксиом у `FirstResearch.candidate`. Это проверка установленного Lean на известном примере, а не приемка недоверенного доказательства.

Для выбранной задачи нужны Lean 4.34.0 и совместимая mathlib. Формальная постановка использует только модули mathlib, импорт всего lean-pool не требуется. Версия mathlib для местной проверки указана в `source.json`.

Lean запускается отдельной проверяющей службой, а не инструментом внутри Coddy. Для команды можно включить автоматическую проверку и ограниченное исправление по диагностике. Успешное чтение `Goal.lean` подтверждает корректность постановки для данной среды, но не наличие доказательства. Даже проверенный кандидат требует рецензии и решения оператора.

## Перед Запуском

1. Подготовить закрытый профиль и повторить предварительную проверку.
2. Добавить исследование из постановки.
3. Запустить цикл через интерфейс: профиль «Coddy: первое исследование», материалы «Lean Pool: ядро матрицы», одна попытка.
4. Подтвердить возможные расходы. Профиль ограничен 300 секундами, 6 шагами и 4096 токенами на ответ модели; точный денежный предел не реализован.
5. При ошибке изучить результат попытки. Цикл автоматически не повторяет неуспешный запрос; неизвестный удаленный исход не доказывает отсутствие расходов.
6. Полученный кандидат проверить отдельно и записать решение о приемке.

Никакая команда подготовки из этой инструкции не дает разрешения на автоматическое начало оплачиваемого исследования.

## Проверки Без Реальной Модели

```sh
CODDY_AGENT_TEST_BINARY="$HOME/.local/bin/coddy" CODDY_AGENT_TEST_VERSION=1.2.54 go test ./internal/execution -run TestCoddyAgentBDD_RealBinaryWithLocalModel -count=1
RESEARCH_TEST_CONTAINER_IMAGE="$(docker image inspect research-team-coddy:local --format '{{.Id}}')" go test ./internal/execution -run TestContainerBDD -count=1
```

Первая проверка использует настоящий файл Coddy и местную подставную модель без действующих учетных данных. Вторая проверяет ограничения контейнера и его удаление после отмены, без обращения к модели.

## Диагностика

`GET /api/attempts/{id}` возвращает состояние попытки, события и, для новых ошибок, `failure_code`: `deadline_exceeded`, `cancelled`, `limit_reached`, `protocol_or_remote_error` или `execution_failed`. События `acp_initialize_failed`, `acp_session_failed`, `acp_configuration_failed` и `acp_prompt_failed` указывают этап отказа.

Необработанные сообщения провайдера и стандартный поток ошибок процесса не сохраняются: они могут содержать учетные данные. Код `protocol_or_remote_error` не устанавливает причину отказа провайдера. Для проверки сети можно выполнить запрос без ключа к адресу провайдера; успешное соединение само по себе не проверяет полномочия ключа или доступность модели.

События `acp_token_limit_reached` и `acp_turn_limit_reached` уточняют достигнутый предел; `acp_empty_response` означает завершение без текста кандидата. При сбое удаления контейнера сохраняется `container_cleanup_failed` вместе с исходной причиной отказа. Уже автоматически удаленный контейнер считается успешно очищенным после проверки его отсутствия.
