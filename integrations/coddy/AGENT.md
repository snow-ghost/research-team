# Подключение Coddy Agent

Coddy Agent написан на Go и выполняет задания отдельным процессом. Coddy Bot управляет задачами GitHub и вызывает программу агента через ACP, протокол взаимодействия клиента с агентом.

| Способ | Настройка | Состояние |
|---|---|---|
| Прямая исследовательская попытка | [coddy-agent.json](../../examples/agents/coddy-agent.json) | Реализован клиент Go; проверен настоящий агент с местной подстановкой модели |
| Агент внутри полного процесса Coddy Bot | [config.coddy-agent.example.yaml](config.coddy-agent.example.yaml) и [agent.example.yaml](agent.example.yaml) | Подготовлены настройки; полный обмен с GitHub требует испытания в выбранном репозитории |

## Версия и сборка

Адаптер допускает Coddy Agent `1.1.64`, `1.2.1` и `1.2.54`. Профиль закрепляет одну точную версию. Для `1.2.54` проверен официальный [выпуск](https://github.com/coddy-project/coddy-agent/releases/tag/1.2.54) с исходниками `cc012f2b890a5a271b40dd15566a43b922669ce3`. Клиентская библиотека: `github.com/coder/acp-go-sdk v0.13.5`.

Ниже сохранен порядок сборки исходной версии `1.1.64` из `aae37407fbe6aedfe81b9f620c9b8cd702d63b0b`. [Исходники этой версии](https://github.com/coddy-project/coddy-agent/tree/aae37407fbe6aedfe81b9f620c9b8cd702d63b0b), [библиотека ACP](https://github.com/coder/acp-go-sdk/tree/v0.13.5).

В проверенной копии исходников агента:

```sh
git rev-parse HEAD
go build -trimpath \
  -ldflags '-X github.com/EvilFreelancer/coddy-agent/internal/version.Version=1.1.64' \
  -o /tmp/coddy-agent-1.1.64 ./cmd/coddy
/tmp/coddy-agent-1.1.64 --version
```

Встроенный путь модуля еще содержит `EvilFreelancer`, поэтому параметр сборки использует это имя. Установка от имени администратора и автоматическое обновление здесь не выполняются. Проверять контрольную сумму и происхождение файла нужно отдельно: строка версии этого не удостоверяет.

Оба проекта обычно используют имя команды `coddy`. Для программы агента выбран отдельный путь, например `/usr/local/bin/coddy-agent`; команды бота вызываются как `python -m coddy`. Это исключает выбор другого проекта через порядок каталогов `PATH`.

## Прямой исполнитель

В примере профиля заменить путь программы, `external.base_url` и `external.model`. Модель указывается без добавленного нами имени подключения `research/`; идентификатор самой модели может содержать `/`. Токен передается через `RESEARCH_CODDY_AGENT_TOKEN`, ссылка на него находится в `secret_env`. Для местного сервера без авторизации это соответствие можно убрать.

Проверка профиля без запуска программы и чтения токена:

```sh
go run ./cmd/research-agent -config examples/agents/coddy-agent.json
```

В подготовленной изолированной среде:

```sh
go run ./cmd/research-agent \
  -config examples/agents/coddy-agent.json \
  -task examples/agents/task.json \
  -execute
```

Этот вызов может расходовать средства поставщика. Адаптер запускает `acp`, проверяет версию протокола, имя и версию программы, создает новую сессию, подтверждает `mode=ask`, модель и `permission_mode=ask`. Он принимает только непустой текст агента при `end_turn`. `max_tokens`, `max_turns` и `max_turn_requests` дают `limit_reached`; частичный текст удаляется.

На каждую попытку создается закрытый временный домашний каталог. Настройки записываются структурированным JSON, который читает YAML-загрузчик Coddy; значение токена в файл не входит. Навыки команды передаются в пакете задания. Автопоиск навыков и правил проекта, память, сжатие контекста, вложенные агенты, обработчики событий проекта и MCP отключены. MCP здесь обозначает протокол подключения дополнительных инструментов.

`max_steps` задает `agent.max_turns`, число оборотов внутреннего цикла Coddy. `max_output_tokens` задает предел ответа модели, а не общий расход. `max_tool_calls` должен быть нулем: общий предел вызовов инструментов не реализован. Учет расхода возвращается как `null`.

Режим `ask` сохраняет собственные инструменты чтения и поиска в сети. Клиент Go не предоставляет файловую систему и терминал через ACP и отклоняет запросы разрешений. Это не ограничивает все действия программы на уровне ОС. Нужны отдельный пользователь или контейнер, доступные только для чтения исходные материалы, ограничения сетевых направлений, диска, памяти и процессов. Поле `operator_managed` лишь фиксирует обязанность оператора.

Ограничение байтов действует отдельно на весь поток ACP и поток ошибок. При отмене или превышении ограничения останавливается группа процессов Linux и закрываются каналы. Доставка `session/cancel` не гарантируется при принудительной остановке; результат вычисления у поставщика может остаться неизвестным. Временная история агента удаляется, долговременный журнал должен вести координатор.

## Внутри Coddy Bot

Использовать настройки бота из `config.coddy-agent.example.yaml`, а настройки агента из `agent.example.yaml`. Пути в первом файле должны соответствовать развертыванию второго. Каталог `/var/lib/research-coddy-agent` отделен от `.coddy` бота. Одновременное использование одного каталога разными развертываниями не проверено.

Бот создает сессию в режиме агента по умолчанию, который допускает изменение файлов. Ограничения прямого клиента Go к этому запуску не применяются. `permission_mode: ask` в настройках агента не означает ручную проверку: изученный клиент Coddy Bot выбирает первый предложенный вариант разрешения. Он также наследует окружение и не проверяет причину завершения перед возвратом текста. [Клиент Coddy Bot](https://github.com/coddy-project/coddy-bot/blob/fc3b9491d76d5911aa78e51fc6494ddf3c21bb77/coddy/worker/agents/acp_agent.py).

Поэтому процесс разработки следует запускать в отдельной среде с ограниченными учетными данными и доступными репозиториями. Нельзя передавать ему токен пользователя соединителя `RESEARCH_GITHUB_TOKEN`. Для рабочего применения требуется отдельная проверка политики разрешений, фильтрации окружения и обработки незавершенного ответа. Новый пример настроек эти ограничения клиента бота не исправляет.

Существующие [соединитель GitHub](../../internal/coddy/README.md), [поправка цикла рецензирования](patches/review-loop-v1.patch) и правила подтверждения публикаций сохраняются.

Проверка настроек агента без сетевых обращений:

```sh
/usr/local/bin/coddy-agent acp --config /etc/research-coddy/agent.yaml -t
```

Параметр `--dry-run` для этой цели не подходит: он проверяет сетевые службы. После локальной проверки нужен опыт с задачей, планом, запросом на слияние и замечанием в закрытом тестовом репозитории.

## Воспроизводимые проверки

Из корня исследовательского проекта:

```sh
go test -race ./...
CODDY_AGENT_TEST_BINARY=/tmp/coddy-agent-1.1.64 \
  go test -race ./internal/execution -run CoddyAgentBDD -count=1
```

Вторая команда запускает настоящий агент только против местного HTTP-сервера с заданными ответами. Она проверяет настройки, согласование ACP, передачу навыков и модели, ограничения инструментов и различение полного и ограниченного ответа. Оплачиваемые обращения и операции GitHub в этом испытании отсутствуют.

Полные траектории, соединение с веб-макетом, приемка доказательств и денежные квоты остаются отдельными задачами. Полученный текст поступает как кандидат и требует предметной приемки.
